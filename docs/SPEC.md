# music-sorter 설계 문서 (정본)

> 이 문서는 music-sorter의 기준 문서다. 설계가 바뀌면 이 문서를 먼저 고친다.
> 상태: **설계 논의 중 (개발 시작 전)**
> 결정 이유는 [DECISIONS.md](DECISIONS.md), 논의 과정은 [HISTORY.md](HISTORY.md)를 본다.

## 1. 목적과 범위

수십만 개 규모의 mp3 파일을 **장르 / 분위기 / 컨셉** 기준으로 자동 분류하고,
PC와 폰의 일반 음악 앱에서 **폴더째 재생**하거나 **태그별로 재생**할 수 있게 한다.

- 분류 근거: 파일 내 메타데이터 + 외부 음원 DB + LLM
- 전체 곡 목록과 태그는 **로컬 SQLite DB** 하나로 관리한다.
- 실행 환경: **Windows** (PC에서 처리하고, 결과 폴더를 폰에 복사해서 사용)
- 예상 규모: 30만 곡 기준 약 2.4TB (곡당 약 8MB)

**하지 않는 것**

- 오디오 분석(소리 자체 분석, 음향 지문 등)
- 음악 파일 삭제 (사용자가 직접 한다)
- 멜론·벅스 등 공식 API가 없는 서비스의 스크래핑

## 2. 설계 원칙

1. **DB가 원본이다.** 파일 태그, 폴더 배치, 재생목록은 DB에서 생성하는 "출력물"이다.
2. **곡은 파일 해시로 식별한다.** 파일을 옮기거나 이름을 바꿔도 정보가 유지된다.
3. **모든 판정에 출처와 신뢰도를 기록한다.** 신뢰도가 낮은 곡은 사람이 검토한다.
4. **수동 입력은 자동 작업이 덮어쓰지 않는다.**
5. **프로그램은 파일을 삭제하지 않는다.** 이동과 이름 변경만 하고, 모두 되돌릴 수 있게 기록한다.
6. **파일을 바꾸는 작업은 미리보기가 기본이다.** 실제 적용은 명시적으로 요청할 때만 한다.
7. **중단 후 이어서 실행할 수 있어야 한다.** 수십만 곡 처리는 며칠이 걸릴 수 있다.
8. **외부 API 응답은 전부 캐시한다.** 같은 조회를 반복하지 않는다.
9. **파일의 기존 고유 정보는 보존한다.** (멜론 PRIV 태그, 가사 등)

## 3. 분류 체계

### 3.1 대분류 (곡당 1개)

| 대분류 | 세부 장르 (1~2개 선택) |
|---|---|
| 가요 | 발라드, 인디/어쿠스틱, 록/밴드, 댄스, 힙합/R&B, 포크 |
| 트로트 | 정통 트로트, 세미/댄스 트로트, 트로트 발라드 |
| 팝 | 발라드, 어쿠스틱, 록, 댄스/일렉트로닉, 힙합/R&B |
| 재즈 | 보컬재즈, 스윙/빅밴드, 보사노바, 라틴재즈, 재즈피아노, 퓨전/스무스 |
| 뉴에이지 | 피아노, 힐링/앰비언트 |
| 클래식 | 피아노, 관현악/협주곡, 실내악, 성악 |
| CCM | 워십/찬양, 발라드, 어쿠스틱, 콰이어/성가, 찬송가 편곡 |
| 기타 | J-POP, 월드뮤직 등 (곡이 많아지면 대분류로 승격) |

- 세부 장르는 경계가 모호한 곡(예: 댄스이면서 록)을 위해 최대 2개까지 허용한다.
- 가요의 `댄스`는 아이돌이 아닌 댄스 가수(예: 싸이)도 포함하도록 `댄스/아이돌`이 아닌 `댄스`로 둔다.

### 3.2 속성 (곡당 1개)

`보컬` / `연주`

모든 대분류에 공통 적용한다.
- 재즈 음악 vs 재즈 보컬 → `재즈` + 속성(`연주`/`보컬`) + 세부 장르 `보컬재즈`
- CCM 노래 vs CCM 연주곡 → `CCM` + 속성
- 예: 찬송가 피아노 연주 → `CCM / 찬송가 편곡 / 연주`

### 3.3 분위기 (1~2개)

`신나는` · `경쾌한` · `설레는` · `잔잔한` · `감성적인` · `슬픈` · `몽환적인` · `웅장한`

비슷한 말(차분한, 잔잔한 등)이 섞이지 않도록 이 8개만 쓴다.

### 3.4 컨셉 (0개 이상)

| 묶음 | 태그 |
|---|---|
| 시즌 | 봄, 여름, 가을, 겨울, 크리스마스 |
| 상황 | 드라이브, 카페, 집중/공부, 수면, 운동, 비오는날, 새벽, 파티/응원 |
| 주제 | 사랑, 이별, 위로, 축가 |
| 신앙 | 예배, 묵상/기도, 감사 |
| 출처 | OST |

- 캐롤과 성탄 CCM은 모두 `크리스마스`로 모인다.
- OST는 장르가 아니라 컨셉으로 둔다.

### 3.5 태그 목록 관리 규칙

- LLM은 **정해진 목록 안에서만** 태그를 고른다.
- 목록에 맞는 태그가 없으면 **"제안 태그"** 칸에 자유롭게 적는다.
- 자주 제안되는 태그는 사람이 검토한 뒤 정식 목록에 추가한다.
- 태그 목록은 코드가 아닌 설정 파일로 관리해서, 목록을 바꿔도 코드를 고치지 않게 한다.

### 3.6 판정 단위

- 모든 판정(대분류 포함)은 **곡 단위**로 한다.
  - 예: 임영웅은 트로트 곡과 발라드 곡이 섞여 있고, 싸이도 댄스곡("강남스타일")과 발라드("기댈 곳")가 섞여 있다.
- 아티스트 정보(주 장르 등)는 캐시해 두고 LLM에 **참고 정보로만** 준다.

### 3.7 분류 예시 (예상)

| 곡 | 대분류 / 세부 | 속성 | 분위기 | 컨셉 |
|---|---|---|---|---|
| 싸이 - 강남스타일 | 가요 / 댄스 | 보컬 | 신나는 | 운동, 파티/응원 |
| 싸이 - 챔피언 | 가요 / 댄스 | 보컬 | 신나는 | 운동, 파티/응원 |
| 싸이 - 예술이야 | 가요 / 댄스 · 록/밴드 | 보컬 | 신나는, 경쾌한 | 드라이브 |
| 싸이 - 기댈 곳 | 가요 / 발라드 · 힙합/R&B | 보컬 | 감성적인 | 위로 |
| 잔나비 - 주저하는 연인들을 위해 | 가요 / 록/밴드 · 인디/어쿠스틱 | 보컬 | 감성적인 | 사랑, 새벽 |
| 권진아 - 끝 | 가요 / 발라드 | 보컬 | 슬픈 | 이별 |
| 이루마 - (피아노곡) | 뉴에이지 / 피아노 | 연주 | 잔잔한 | 카페, 수면 |

## 4. 입력 데이터

### 4.1 메타데이터 등급

mp3마다 메타데이터 수준이 크게 다르다. 곡마다 등급을 매겨 DB에 기록한다.

| 등급 | 예 | 가진 정보 |
|---|---|---|
| A | 멜론 정식 다운로드 | 제목, 아티스트, 앨범, 트랙, 발매일, 장르, 가사, 멜론 곡·앨범 ID (PRIV 태그) |
| B | 일반 태그 파일 | 제목, 아티스트, 앨범 일부 |
| C | 변환 파일 등 | 제목, 아티스트, 커버만 |
| D | 태그 없음 | 파일 이름뿐 |

### 4.2 샘플 조사 결과 (2026-09-30, 454곡)

- 멜론 정식 파일(A등급)은 1곡, 나머지 453곡은 C등급(48kHz, LAME 3.100 인코딩, 제목·아티스트·커버만)
- 장르 태그가 있는 곡은 1곡(멜론 파일의 `Rock`)
- 같은 곡이 출처만 달리해서 두 벌 있는 사례가 있다. (길이 4:25 vs 4:27, 파일 해시도 다름)
- 파일 이름 형식이 섞여 있다. (`아티스트 - 제목`, `아티스트-08-제목`)

### 4.3 시사점

- 파일 안의 장르 태그는 거의 없거나 믿을 수 없다. 장르는 외부 정보와 LLM으로 판정한다.
- 파일 이름은 규칙으로 먼저 파싱하고, 실패한 것만 LLM에 맡긴다.
- 중복은 파일 해시나 길이 일치만으로는 잡을 수 없다. (§11)

## 5. 처리 흐름

```
1. 스캔        폴더의 mp3를 찾아 해시, 태그, 음질 정보를 DB에 기록
2. 파싱        태그와 파일 이름에서 아티스트·제목 확정 (NFC 정규화 포함)
3. 외부 조회    MusicBrainz, Last.fm 정보 수집 (캐시)
4. 분류        LLM으로 대분류·세부 장르·속성·분위기·컨셉 판정
5. 재판정       신뢰도 낮은 곡만 상위 모델로 다시 판정
6. 검토        여전히 낮은 곡, 제안 태그, 중복 후보를 사람이 검토
7. 적용        파일 이름 정리, 대분류 폴더 이동, ID3 장르 기록 (미리보기 후 적용)
8. 내보내기     태그별 m3u 재생목록 생성
```

- 각 단계는 따로 실행할 수 있고, 처리 상태는 곡마다 DB에 기록한다.
- 새 곡이 추가되면 새 곡만 처리한다.

## 6. 외부 정보 출처

| 출처 | 용도 | 비고 |
|---|---|---|
| MusicBrainz | 곡·아티스트 식별, 앨범·발매일 보완 | 초당 1건 제한 (30만 곡 조회 시 약 3.5일), User-Agent에 연락처 필수, 가요 정보는 약함 |
| Last.fm 태그 | 세부 장르, 분위기, 컨셉 근거 | `bossa nova`, `christmas`, `chill` 같은 사용자 태그가 풍부함, API 키 필요 |
| LLM | 최종 판정 | 수집한 정보 + 자체 지식으로 정해진 목록 안에서 선택 (§7) |

- 멜론·벅스 등은 장르 정보는 좋지만 공식 API가 없고 스크래핑은 약관 문제가 있어 사용하지 않는다.
- 단, 파일 안에 이미 들어 있는 멜론 태그 정보는 사용한다.

## 7. LLM 사용 방식

### 7.1 모델

| 용도 | 모델 |
|---|---|
| 1차 분류 (전체 곡) | **Claude Haiku 4.5** (`claude-haiku-4-5`) |
| 재판정 (신뢰도 낮은 곡) | **Claude Sonnet 5.5** (`claude-sonnet-5-5`) |

- 분류 작업 자체는 쉽지만, 정보가 적은 한국 곡에 대한 **모델의 지식**이 정확도를 좌우한다.
  가장 저렴한 등급(nano, Flash-Lite)은 모르는 곡을 지어낼 위험이 커서 한 단계 위 등급을 쓴다.
- 코드는 특정 LLM 서비스에 묶이지 않게 만든다. 모델 이름은 설정으로 바꿀 수 있게 한다.

### 7.2 호출 방식

- 한 번에 여러 곡(약 20곡)을 묶어서 요청한다.
- **Batch API**를 써서 비용을 50% 줄인다. (실시간 응답이 필요 없는 작업)
- 태그 목록 등 공통 지시문은 **프롬프트 캐싱**으로 재사용한다.
- 응답은 정해진 JSON 형식(구조화 출력)으로 받는다. 곡마다 신뢰도와 제안 태그를 포함한다.
- 외부 정보가 전혀 없는 곡은 "모름"을 허용한다. 억지로 판정하지 않고 `_미분류`로 둔다.

### 7.3 정확도 확인

- 개발 초기에 사용자가 직접 정답을 단 **100~200곡 샘플**로 정확도를 측정한다.
- 이 결과로 지시문과 신뢰도 기준값을 조정한다.

### 7.4 예상 비용 (2026-10-01 기준 추정)

조건: 30만 곡, 곡당 입력 약 200토큰·출력 약 100토큰, 20곡씩 묶음, Batch 50% 할인, 공통 지시문 캐시.

| 모델 | 가격 (입력/출력, 100만 토큰당) | 30만 곡 예상 |
|---|---|---|
| Claude Haiku 4.5 (채택) | $1.00 / $5.00 | 약 $105 |
| Claude Sonnet 5.5 (재판정용) | $2.00 / $10.00 | 전체 시 약 $210, 10%만 재판정 시 약 $20 |
| GPT-5.4 mini (검토) | $0.75 / $4.50 | 약 $90 |
| GPT-5.4 nano (검토) | $0.20 / $1.25 | 약 $25 |
| Gemini 3.1 Flash-Lite (검토) | $0.25 / $1.50 | 약 $30 |

- 전체 예상: **한 번에 $100~150 정도**. 이후 추가되는 곡은 소량이라 비용이 거의 없다.
- GPT·Gemini 가격은 제3자 정리 자료 기준이므로 참고용이다.

## 8. DB 개념 설계 (SQLite)

```
tracks      : 파일 경로, 파일 해시, 제목, 아티스트, 앨범, 길이, 비트레이트, 샘플레이트,
              메타데이터 등급, 대분류, 속성, 처리 상태
artists     : 아티스트 정보 캐시 (참고용 주 장르 등)
tags        : 태그 이름 + 종류(세부장르/분위기/컨셉) + 묶음
track_tags  : 곡-태그 연결 + 출처(LLM/Last.fm/수동) + 신뢰도
suggested   : LLM이 제안한 목록 외 태그
api_cache   : 외부 API 응답 원본
file_ops    : 이름 변경·이동·태그 기록 이력 (되돌리기용)
```

## 9. 출력

### 9.1 대상 환경

- PC: 곰오디오
- 폰: 삼성 뮤직
- 폰에는 PC의 음악 폴더를 **통째로 복사**해서 사용한다.
- 두 앱 모두 "태그로 걸러서 재생" 기능이 약하다. 확실하게 되는 것은 **장르 탐색**과 **m3u 재생목록**이다.

### 9.2 mp3 파일 태그

- ID3 장르 필드에는 **대분류만** 기록한다. (두 앱 모두 장르 탐색 가능)
- 세부 장르, 분위기, 컨셉은 파일에 쓰지 않는다.
  태그를 고칠 때마다 파일이 바뀌어 폰으로 다시 복사해야 하기 때문이다.
- 파일 기록은 분류 결과가 안정된 뒤 **한 번에** 한다.
  처음 기록할 때는 모든 파일이 바뀌므로 폰으로 전체를 다시 복사해야 한다.

### 9.3 폴더 구조

음악 파일은 **대분류 폴더**로 나눈다.

```
MUSIC_ROOT/
  가요/
    잔나비 - 주저하는 연인들을 위해.mp3
  트로트/  팝/  재즈/  뉴에이지/  클래식/  CCM/  기타/
  _미분류/        분류 전이거나 판정 실패한 곡
  _중복검토/      §11 참고
  _삭제예정/      §11 참고
  [분위기] 잔잔한.m3u
  ...
```

- 대분류가 바뀌면 파일도 해당 폴더로 옮긴다. (이동 기록은 `file_ops`에 남긴다)
- `_`로 시작하는 폴더는 프로그램이 관리하는 작업 폴더다.

### 9.4 재생목록 (m3u)

m3u는 곡 파일 경로 목록만 담은 텍스트 파일이다. 곡을 복사하지 않고 여러 재생목록에 같은 곡을 넣을 수 있다.

- 세부 장르, 분위기, 컨셉별 재생목록을 생성한다.
- m3u는 음악 폴더 최상위에 두고 **상대 경로**를 쓴다. 폴더째 복사해도 동작한다.
  - 예: `가요/잔나비 - 주저하는 연인들을 위해.mp3`
  - 경로 구분자는 PC와 폰 모두에서 동작하도록 `/`를 쓴다. (앱 테스트로 확인 필요)
- m3u는 항상 DB에서 새로 생성한다. 파일이 이동해도 경로가 자동으로 맞춰진다.
- 파일 이름 예: `[장르] 재즈 - 보사노바.m3u`, `[분위기] 잔잔한.m3u`, `[컨셉] 크리스마스.m3u`, `[CCM] 연주.m3u`
- 조합 재생목록(예: 가요 + 잔잔한 + 비오는날)은 모든 조합을 미리 만들지 않고, 필요할 때 DB에서 생성한다.

## 10. 파일 이름 정리

- 형식: `아티스트 - 제목.mp3`
- 모든 변경을 `file_ops`에 기록해서 되돌릴 수 있게 한다.
- Windows 파일 이름 제약을 처리한다.
  - 사용할 수 없는 문자(`\ / : * ? " < > |`)는 비슷한 문자로 바꾼다.
  - 같은 이름이 이미 있으면 번호를 붙인다.
  - 경로가 매우 긴 경우도 처리한다.
- **한글 자모 정규화(NFC)**: 맥에서 온 파일 이름은 한글이 자모 단위로 분리(NFD)되어 있을 수 있다.
  이름 비교와 저장 전에 항상 NFC로 정규화한다. 이렇게 하지 않으면 같은 이름이 다르게 인식된다.

## 11. 중복 곡 처리

오디오 분석을 하지 않으므로 **"아티스트와 제목이 같고 길이가 비슷하면 중복 후보"**로 잡는다.
최종 판단은 **사용자가 직접 듣고** 한다.

```
_중복검토/
  잔나비 - 주저하는 연인들을 위해/
    [추천] 320k 44.1kHz 멜론 - 잔나비-08-주저하는 연인들을 위해.mp3
    320k 48kHz - 잔나비 - 주저하는 연인들을 위해.mp3
```

1. 중복 후보를 곡별 하위 폴더로 모은다.
2. 파일 이름 앞에 음질 정보와 추천 표시를 붙인다.
3. 사용자가 고르면, 선택한 곡은 원래 자리로 돌아가고 나머지는 `_삭제예정/`으로 옮긴다.
4. 실제 삭제는 사용자가 직접 한다.

**추천 기준** (비트레이트 숫자만으로는 판단하지 않는다. 저음질을 320k로 재변환한 파일이 있을 수 있다.)

1. 출처 신뢰도 (멜론 등 정식 다운로드 태그 우선)
2. 비트레이트, 샘플레이트
3. 메타데이터 완성도

## 12. 기술 스택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | **Python** (3.13) | 필요한 라이브러리가 모두 있고, 개발 PC에 이미 설치됨 |
| mp3 태그 | mutagen | 읽기·쓰기 모두 지원, PRIV 등 기존 프레임 보존 가능 |
| DB | sqlite3 (표준 라이브러리) | 별도 설치 불필요 |
| LLM | Anthropic 공식 SDK | §7 |
| 형태 | 명령어(CLI) 프로그램 | 예: `music-sorter scan`, `music-sorter classify`. 필요하면 나중에 GUI나 exe로 확장 |
