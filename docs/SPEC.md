# music-sorter 설계 문서 (정본)

> 이 문서는 music-sorter의 기준 문서다. 설계가 바뀌면 이 문서를 먼저 고친다.
> 상태: **개발 진행 중 — 로컬 관리·파일 출력 구현, 자동 분류 연결 진행**. 2026-10-07 사용자가 "개발 시작"을 명시했다. 구현·검증 현황은 §17에 기록한다.
> 2026-10-07: 사용자가 남은 설계 판단을 위임하여 권장안을 채택했다. 아래 수치·동작은 설계 요구사항이며 실행 결과가 아니다.
> 결정 이유는 [DECISIONS.md](DECISIONS.md), 논의 과정은 [HISTORY.md](HISTORY.md)를 본다.

## 1. 목적과 범위

수십만 개 규모의 mp3 파일을 **장르 / 분위기 / 컨셉** 기준으로 자동 분류하고,
PC와 폰의 일반 음악 앱에서 **폴더째 재생**하거나 **태그별로 재생**할 수 있게 한다.

- 분류 근거: 파일 내 메타데이터 + 외부 음원 DB + LLM
- 전체 곡 목록과 태그는 **로컬 SQLite DB** 하나로 관리한다.
- 실행 환경: **Windows** (PC에서 처리하고, 결과 폴더를 폰에 복사해서 사용)
- 예상 규모: 30만 곡 기준 약 2.4TB (곡당 약 8MB)

**하지 않는 것**

- 오디오 분석(소리 자체 분석, 음향 지문 등)
- 음악 파일 영구 삭제·자동 삭제 (중복 비교의 명시적 휴지통 이동만 지원)
- 음원·가사·개인 계정 정보의 외부 자동 수집, 로그인·접근 차단 우회

## 2. 설계 원칙

1. **DB가 원본이다.** 파일 태그, 폴더 배치, 재생목록은 DB에서 생성하는 "출력물"이다.
2. **파일은 변하지 않는 내부 파일 ID로 식별한다.** 경로와 해시는 현재 상태를 나타내며, 이동·이름 변경·프로그램의 태그 수정 뒤에도 내부 ID를 유지한다. 같은 곡의 서로 다른 파일은 별도로 관리한다. (§8.1)
3. **모든 판정에 출처와 신뢰도를 기록한다.** 신뢰도가 낮은 곡은 사람이 검토한다.
4. **수동 입력은 자동 작업이 덮어쓰지 않는다.** 분류 항목별 보호 단위와 해제 동작은 §3.9를 따른다.
5. **프로그램은 음악 파일을 영구 삭제하지 않는다.** 중복 비교에서 사용자가 선택·확인한 파일만 Windows 휴지통으로 이동하며 복원은 휴지통에서 한다 (§11.2). 이동·이름 변경·태그 기록은 모두 되돌릴 수 있게 기록한다.
6. **파일을 바꾸는 작업은 미리보기가 기본이다.** 실제 적용은 명시적으로 요청할 때만 한다.
7. **중단 후 이어서 실행할 수 있어야 한다.** 수십만 곡 처리는 며칠이 걸릴 수 있다.
8. **외부 API 응답은 전부 캐시한다.** 같은 조회를 반복하지 않는다.
9. **파일의 기존 고유 정보는 보존한다.** (멜론 PRIV 태그, 가사 등)

## 3. 분류 체계

### 3.1 대분류 (곡당 1개)

| 대분류 | 세부 장르 (1~2개 선택) |
|---|---|
| 가요 | 발라드, 인디/어쿠스틱, 록/밴드, 댄스, 힙합/R&B, 포크 |
| 트로트 | 정통 트로트, 세미/댄스 트로트, 트로트 발라드 |
| 팝 | 발라드, 어쿠스틱, 록, 댄스/일렉트로닉, 힙합/R&B |
| 재즈 | 보컬재즈, 스윙/빅밴드, 보사노바, 라틴재즈, 재즈피아노, 퓨전/스무스 |
| 뉴에이지 | 피아노, 힐링/앰비언트 |
| 클래식 | 피아노, 관현악/협주곡, 실내악, 성악 |
| CCM | 워십/찬양, 발라드, 어쿠스틱, 콰이어/성가, 찬송가 편곡, 재즈, 클래식 |
| 기타 | J-POP, 월드뮤직 (추가·대분류 승격은 목록 관리에서 명시적으로 결정) |

- 세부 장르는 경계가 모호한 곡(예: 댄스이면서 록)을 위해 최대 2개까지 허용한다.
- 가요의 `댄스`는 아이돌이 아닌 댄스 가수(예: 싸이)도 포함하도록 `댄스/아이돌`이 아닌 `댄스`로 둔다.

### 3.2 속성 (곡당 1개)

`보컬` / `연주`

모든 대분류에 공통 적용한다.
- 재즈 음악 vs 재즈 보컬 → `재즈` + 속성(`연주`/`보컬`) + 세부 장르 `보컬재즈`
- CCM 노래 vs CCM 연주곡 → `CCM` + 속성
- 예: 찬송가 피아노 연주 → `CCM / 찬송가 편곡 / 연주`

### 3.3 분위기 (1~2개)

`신나는` · `경쾌한` · `설레는` · `잔잔한` · `감성적인` · `슬픈` · `몽환적인` · `웅장한`

비슷한 말(차분한, 잔잔한 등)이 섞이지 않도록 이 8개만 쓴다.

### 3.4 컨셉 (0개 이상)

| 묶음 | 태그 |
|---|---|
| 시즌 | 봄, 여름, 가을, 겨울, 크리스마스 |
| 상황 | 드라이브, 카페, 집중/공부, 수면, 운동, 비오는날, 새벽, 파티/응원 |
| 주제 | 사랑, 이별, 위로, 축가 |
| 신앙 | 예배, 묵상/기도, 감사 |
| 출처 | OST |

- 캐롤과 성탄 CCM은 모두 `크리스마스`로 모인다.
- OST는 장르가 아니라 컨셉으로 둔다.

### 3.5 태그 목록 관리 규칙

- LLM은 **정해진 목록 안에서만** 태그를 고른다.
- 목록에 맞는 태그가 없으면 **"제안 태그"** 칸에 자유롭게 적는다.
- 자주 제안되는 태그는 사람이 검토한 뒤 정식 목록에 추가한다.
- 태그 목록은 코드가 아닌 설정 파일로 관리해서, 목록을 바꿔도 코드를 고치지 않게 한다.

### 3.6 판정 단위

- 모든 판정(대분류 포함)은 **곡 단위**로 한다.
  - 예: 임영웅은 트로트 곡과 발라드 곡이 섞여 있고, 싸이도 댄스곡("강남스타일")과 발라드("기댈 곳")가 섞여 있다.
- 아티스트 정보(주 장르 등)는 캐시해 두고 LLM에 **참고 정보로만** 준다.

### 3.7 분류 예시 (예상)

| 곡 | 대분류 / 세부 | 속성 | 분위기 | 컨셉 |
|---|---|---|---|---|
| 싸이 - 강남스타일 | 가요 / 댄스 | 보컬 | 신나는 | 운동, 파티/응원 |
| 싸이 - 챔피언 | 가요 / 댄스 | 보컬 | 신나는 | 운동, 파티/응원 |
| 싸이 - 예술이야 | 가요 / 댄스 · 록/밴드 | 보컬 | 신나는, 경쾌한 | 드라이브 |
| 싸이 - 기댈 곳 | 가요 / 발라드 · 힙합/R&B | 보컬 | 감성적인 | 위로 |
| 잔나비 - 주저하는 연인들을 위해 | 가요 / 록/밴드 · 인디/어쿠스틱 | 보컬 | 감성적인 | 사랑, 새벽 |
| 권진아 - 끝 | 가요 / 발라드 | 보컬 | 슬픈 | 이별 |

### 3.8 미확정 분류와 별도 보관

> **확정:** LLM 분류·재판정 후에도 미확정 항목이 남은 곡은 별도 폴더로 모아 보관한다. 대분류 경계·우선순위는 §3.10을 따른다.

- 대분류·세부 장르·보컬/연주·분위기·컨셉은 각각 독립적으로 판정한다. 한 항목을 알 수 없다고 다른 항목의 판정을 지우지 않는다.
- 근거가 부족한 항목은 값을 억지로 채우지 않고 `미확정` 상태로 둔다. 기존 §3의 선택 개수는 판정이 확정된 항목에 적용하고, 미확정 항목은 비어 있을 수 있다.
- `미확정`은 음악 태그가 아닌 처리 상태로 관리한다. 재판정·사람 검토가 필요한 이유를 항목별로 표시한다.
- 컨셉은 `판정하지 못함`과 `검토했으나 해당 태그 없음`을 구분한다. 두 경우 모두 목록은 비어 있을 수 있으므로 상태를 함께 기록한다.
- LLM 처리 완료 후에도 하나 이상의 항목이 미확정이면 대분류가 확정되어 있어도 `_미확정/` 보관 계획을 만든다. 단, 중복 검토 중에는 후보 보관을 우선하며 폴더 보관을 선택하지 않으면 위치 변경을 보류하고 GUI에서 비교한다 (§11). 먼저 제안했던 '대분류 폴더에 두고 미확정 항목만 검토' 방식을 대체한다.
- 이미 확정된 항목, 수동 수정, 미확정 이유, 모델·판정 이력은 DB에 보존한다. 보관 폴더로 옮겼다고 분류 결과를 초기화하지 않는다.
- 1차 분류 뒤 재판정을 기다리는 상태와, 예정한 LLM 처리 이후에도 미확정인 상태를 구분한다. `_미확정` 보관 대상은 후자다. 재판정을 사용하지 않는 작업은 1차 분류 결과를 기준으로 한다.
- API 호출 실패·처리 중단으로 판정을 받지 못한 상태는 분류 결과의 미확정과 구분한다. 작업 실패를 미확정 판정으로 확정하지 않는다.
- 별도 보관 이동도 파일 정리 미리보기 후 실제 적용을 요청했을 때 수행하고 `file_ops`에 기록한다. 분류 응답을 받거나 DB를 수정하는 것만으로 이동하지 않는다.
- 미확정 항목을 재판정 또는 사람이 검토하여 해결하면 해당 대분류 폴더로 옮기는 계획을 제시한다. 중복 검토 중인 파일은 검토가 끝날 때까지 후보와 함께 둔다. 복귀도 미리보기·명시적 적용을 따르며 내부 ID와 이력은 유지한다.
- 파일 누락·외부 변경·연결 보류 등 파일 상태가 이동을 막는 경우는 보관 이동도 보류한다. 일반 파일 변경·복구 원칙은 그대로 따른다.
- 미확정 곡은 일반 재생목록에서 제외하고 별도의 `미확정 곡` 검토용 재생목록으로 모은다 (§9.4). 포함 여부는 보관 폴더 이동 여부가 아닌 DB의 분류 상태로 판단한다.
- 미확정 항목이 남은 곡은 기존 ID3 장르 태그를 유지한다. 모든 분류 항목이 확정된 뒤 미리보기·명시적 적용으로 대분류를 기록한다 (§9.2).
- 중복 후보이면서 미확정인 곡을 폴더 보관하면 `_중복검토`를 사용하되 미확정 상태·기존 ID3 유지·검토용 재생목록 정책은 그대로 따른다. 검토 후 남길 파일이 미확정이면 `_미확정`, 모든 분류가 확정됐으면 대분류 폴더 배치를 계획한다 (§11).
- 신뢰도·근거·확정 상태도 항목별로 기록한다. 자동 확정·재판정 임계값은 정답 샘플 평가 후 정한다. 모델이 제시한 신뢰도를 실제 정답 확률로 취급하지 않는다.

### 3.9 수동 분류 보호

- 보호 단위는 곡의 분류 항목별로 둔다. `대분류 / 세부 장르 / 보컬·연주 / 분위기 / 컨셉`을 각각 독립적으로 보호한다.
- 사용자가 직접 수정해 저장한 항목은 수동 보호 상태로 둔다. 세부 장르·분위기·컨셉처럼 여러 값을 갖는 항목은 개별 태그가 아닌 해당 항목의 목록 전체를 보호한다. 컨셉을 검토하고 `해당 태그 없음`으로 저장한 빈 목록도 보호한다.
- 자동 분류·재판정·외부 정보 보완은 보호된 항목의 값과 판정 상태를 덮어쓰거나 태그를 추가·제거하지 않는다. 다른 항목은 기존 분류 규칙에 따라 자동 갱신할 수 있다. 진행 중인 요청 결과를 반영할 때도 현재 보호 상태를 확인한다.
- 사용자가 해당 항목의 `자동 분류로 되돌리기`를 선택하면 그 항목의 보호만 해제한다. 보호 해제 자체로 API 호출·파일 변경을 시작하지 않으며, 이후 별도로 실행하는 자동 분류에서 해당 항목을 갱신할 수 있다.
- 곡 상세 화면에서 항목별 수동 보호 여부와 해제 동작을 표시한다. 수동 수정·보호 해제와 이전 값은 DB 이력에 보존하고, 파일 변경은 기존 미리보기·명시적 적용 절차를 따른다.
- 자동 변경 제안이 수동 보호된 값과 충돌하면 해당 변경을 보류한다. 예를 들어 대분류 변경으로 보호된 세부 장르가 허용 목록과 맞지 않으면 기존 대분류·세부 장르와 보호 상태를 유지한다. 충돌하는 조합을 현재 분류로 확정하거나 보호를 자동 해제하지 않는다.
- 보류한 판정은 기존 분류와 분리한 변경 제안으로 DB에 보존하고, 검토 화면에 기존 값·제안 값·충돌 이유를 함께 표시한다. 서로 연관된 변경은 함께 보류하여 일부만 반영한 잘못된 조합을 만들지 않는다. 충돌하지 않는 다른 항목은 기존 보호 규칙에 따라 갱신할 수 있다.
- 사용자는 기존 분류 유지로 제안을 거절하거나, 새 대분류와 그 허용 목록에 맞는 세부 장르를 함께 선택해 해결한다. 변경 제안의 존재만으로 기존 판정을 미확정으로 바꾸거나 파일 배치를 변경하지 않는다. 검토 결과는 DB 이력에 남기고 파일 변경은 별도로 미리보기·적용한다.

### 3.10 분류 경계와 우선순위

다음은 보편적인 음악학 분류를 주장하는 기준이 아니라 **이 라이브러리의 운영 규칙**이다. 곡의 실제 녹음·편곡에 관한 근거를 우선하고 아티스트 국적·이름·앨범 제목만으로 확정하지 않는다.

| 판단 순서 | 기준 |
|---|---|
| 1. CCM | 찬양·예배 목적 또는 식별된 찬송가·기독교 곡의 편곡이라는 근거가 있으면 CCM. 재즈·클래식 편곡 성격은 CCM 세부 장르로 보존한다. 종교 가수라는 이유만으로 모든 곡을 CCM에 넣지 않는다 |
| 2. 녹음의 음악 성격 | 클래식 레퍼토리를 클래식 방식으로 연주한 녹음은 클래식, 재즈로 재해석한 녹음은 재즈. 트로트 성격이 확인되면 트로트. 뉴에이지·앰비언트 성격이 확인되면 뉴에이지. 이 항목들 사이에는 이름순의 강제 우선순위를 두지 않고 녹음·편곡 근거로 결정한다 |
| 3. 가요·팝 | 위 범주가 아닌 대중음악은 한국 대중음악 발매·활동 맥락이면 가요, 서구권·국제 팝 발매 맥락이면 팝. 가사 언어나 국적 하나만으로 갈라 넣지 않으며 영어로 부른 한국 대중음악도 가요가 될 수 있다 |
| 4. 기타 | J-POP·월드뮤직 등 음악 성격을 알고 있으나 현재 대분류에 맞지 않는 곡. 정체를 모르는 곡을 기타로 채우지 않는다 |
| 5. 미확정 | 녹음 식별이나 경계 판단 근거가 부족하거나 충돌하면 미확정. 1차·재판정·사람 검토 흐름은 §3.8을 따른다 |

- 연주곡이라는 이유만으로 뉴에이지에 넣지 않는다. 팝·가요의 반주 버전, 재즈 연주, 클래식 연주와 구분한다. OST·크리스마스·예배 같은 컨셉만으로 장르를 바꾸지 않는다.
- 커버는 원곡의 장르를 그대로 상속하지 않고 해당 녹음의 연주·편곡 정보를 참고한다. 동명이곡·커버·리믹스·라이브는 §6.1의 식별 기준을 따른다.
- 세부 장르는 선택된 대분류의 허용 목록에서만 1~2개 고른다. CCM에 재즈·클래식을 추가한 목록을 다음 분류 규칙 버전으로 기록한다. 기존 판정을 자동 재분류하지 않는다.
- 분위기·컨셉은 제목의 단어 하나로 추정하지 않는다. 외부 근거와 곡 식별을 확인하고, 근거가 부족하면 해당 항목만 미확정으로 남긴다. `해당 컨셉 없음`과 `알 수 없음`을 구분한다.
- 태그 목록에 없는 스타일은 제안 태그로 보존한다. 사용자가 제안을 승인할 때 목록 버전과 영향을 받을 곡 수를 보여주고 재분류는 별도 실행한다.

## 4. 입력 데이터

### 4.1 메타데이터 등급

mp3마다 메타데이터 수준이 크게 다르다. 곡마다 등급을 매겨 DB에 기록한다.

| 등급 | 예 | 가진 정보 |
|---|---|---|
| A | 멜론 정식 다운로드 | 제목, 아티스트, 앨범, 트랙, 발매일, 장르, 가사, 멜론 곡·앨범 ID (PRIV 태그) |
| B | 일반 태그 파일 | 제목, 아티스트, 앨범 일부 |
| C | 변환 파일 등 | 제목, 아티스트, 커버만 |
| D | 태그 없음 | 파일 이름뿐 |

### 4.2 샘플 조사 결과 (2026-09-30, 454곡)

- 멜론 정식 파일(A등급)은 1곡, 나머지 453곡은 C등급(48kHz, LAME 3.100 인코딩, 제목·아티스트·커버만)
- 장르 태그가 있는 곡은 1곡(멜론 파일의 `Rock`)
- 같은 곡이 출처만 달리해서 두 벌 있는 사례가 있다. (길이 4:25 vs 4:27, 파일 해시도 다름)
- 파일 이름 형식이 섞여 있다. (`아티스트 - 제목`, `아티스트-08-제목`)

### 4.3 시사점

- 파일 안의 장르 태그는 거의 없거나 믿을 수 없다. 장르는 외부 정보와 LLM으로 판정한다.
- 파일 이름은 규칙으로 먼저 파싱하고, 실패한 것만 LLM에 맡긴다.
- 중복은 파일 해시나 길이 일치만으로는 잡을 수 없다. (§11)

## 5. 처리 흐름

```
1. 스캔        폴더의 mp3를 찾아 해시, 태그, 음질 정보를 DB에 기록
2. 파싱        태그와 파일 이름에서 아티스트·제목 확정 (NFC 정규화 포함)
3. 외부 조회    MusicBrainz, Last.fm 정보 수집 (캐시)
4. 분류        LLM으로 대분류·세부 장르·속성·분위기·컨셉 판정
5. 재판정       신뢰도 낮은 곡만 상위 모델로 다시 판정
6. 검토        미확정·낮은 신뢰도 곡, 제안 태그, 중복 후보를 사람이 검토
7. 적용        이름 정리, 대분류 배치·미확정 보관 이동, ID3 장르 기록 (미리보기 후 적용)
8. 내보내기     태그별 m3u 재생목록 생성
```

- 각 단계는 따로 실행할 수 있고, 처리 상태는 곡마다 DB에 기록한다.
- 새 곡이 추가되면 새 곡만 처리한다.

| 출처 | 용도 | 비고 |
|---|---|---|
| MusicBrainz | 곡·아티스트 식별, 앨범·발매일 보완 | 초당 1건 제한 (30만 곡 조회 시 약 3.5일), User-Agent에 연락처 필수, 가요 정보는 약함 |

| 멜론·벅스·지니 | 국내 곡 식별 후보·곡/앨범 장르의 출처 비교 | 공개 검색·상세 조회, 별도 키 없음. 장르 충돌·정보 범위는 §6.2 적용 |
| LLM | 최종 판정 | 수집한 정보 + 자체 지식으로 정해진 목록 안에서 선택 (§7) |

- 2026-10-09 사용자의 구현 지시에 따라 국내 공개 검색과 곡/앨범 정보의 제한된 조회를 추가한다. 기존 D25의 일괄 제외를 대체한다. 멜론·벅스의 공개 검색/상세를 우선 대조하고 충돌·근거 부족 시 지니를 추가 검색한다. 세 사이트의 곡 상세 URL을 직접 추가해 대조할 수도 있다. 계정 로그인·음원·가사·검색 요약을 분류 근거로 수집하지 않는다. HTTP 차단·응답 형식 변경은 오류로 남기고 우회하지 않는다.
- 단, 파일 안에 이미 들어 있는 멜론 태그 정보는 사용한다.

### 6.2 국내 검색과 출처 대조

- 검색·상세 조회·항목 비교는 프로그램이 수행한다. LLM은 확인된 근거로 최종 분류를 판단하며 조회 자체에는 LLM을 호출하지 않는다. 기본 국내 검색은 멜론·벅스 공개 검색을 사용해 추가 키 없이 제공한다. 설정에서 사용 여부를 바꿀 수 있다. 전송은 제목·아티스트뿐이며 조회는 명시적 곡 정보 찾기에서만 실행한다.
- 제목·아티스트·버전·선택적 길이를 먼저 확인한다. 아티스트 페이지의 명시적 괄호 별칭은 비교에 쓸 수 있지만 제목의 버전 표기는 제거하지 않는다. 다른 아티스트·커버·라이브·리믹스는 제외한다. 동일 출처의 여러 발매는 후보별로 보존하고 한 표로만 센다. 국내 정보는 MusicBrainz 녹음 ID를 자동 연결하는 근거로 쓰지 않는다.
- 공식 곡 장르와 앨범 장르를 구분한다. 벅스의 곡 상세에 장르가 없으면 연결된 앨범 정보도 조회한다. 앨범에 해당 곡 하나만 있을 때만 그 장르를 곡의 참고 장르로 대조하고, 여러 곡 앨범 장르는 전체 앨범 참고 정보로 표시한다. 발매일은 각 발매의 값으로 유지하며 서로 다른 앨범의 날짜를 다수결로 합치지 않는다.
- 두 출처 이상이 같은 장르 집합을 제공하고 다른 곡 장르와 충돌하지 않으면 `여러 출처에서 일치`로 표시한다. 서로 다른 장르 집합이면 `출처마다 정보가 다름`, 확인 가능한 장르 출처가 하나뿐이면 `근거 부족`으로 남긴다. 출처 수는 독립적인 원자료 수나 정답 확률을 뜻하지 않는다. 추가 곡 상세 URL로 제3 출처를 대조할 수 있다.
- 원문 항목·범위·출처 URL·조회 시점·제외 이유·일치/충돌을 캐시한다. LLM에는 대조에서 일치한 장르와 상태·URL만 좁은 계약으로 전달하고 충돌한 장르를 임의로 확정하지 않도록 지시한다. 기존 완료 분류와 파일 메타데이터는 조회만으로 변경하지 않는다.
- HTTPS 및 정해진 멜론/벅스/지니 호스트·공개 경로만 조회한다. 응답 크기·시간·후보 수를 제한하고 사이트별 공유 간격으로 순차 조회한다. URL의 인증 정보·포트·조각·리디렉션과 임의 호스트는 거부한다. HTML의 스크립트·가사·사용자 댓글은 근거에 포함하지 않는다. 비교 UI는 결과 선택·출처 열기·추가 출처·재조회·중단을 제공한다.

### 6.1 외부 곡 식별과 근거 사용

- 내부 파일 ID, 외부 녹음 ID, 작품·앨범 ID를 구분한다. MusicBrainz의 `recording`을 녹음 연결의 기준으로 사용하고 여러 녹음을 같은 작품이라는 이유로 병합하지 않는다. [MusicBrainz Recording 정의](https://musicbrainz.org/doc/Recording).
- 제목·아티스트 비교는 NFC·공백·대소문자 정규화로 시작한다. 원문을 보존하고 `Live / Remix / Instrumental / Acoustic / Remaster` 같은 버전 정보와 피처링 참여자 정보를 지우지 않는다. 아티스트 별칭은 검증된 연결이 있을 때만 사용한다.
- 유효한 외부 녹음 ID가 있는 경우에도 제목·아티스트·버전을 대조한다. ID가 없으면 제목·아티스트·버전이 일치하고 앨범·길이 등 보조 정보가 모순되지 않는 유일한 후보만 자동 연결한다. 검색 점수만으로 확정하지 않는다.
- 기존 ID3의 MusicBrainz UFID/녹음 ID와 ISRC를 검증해 우선 조회한다. ID가 여러 개거나 조회 결과가 모순되면 연결을 보류하고 검색으로 조용히 대체하지 않는다. 보류 후보의 제목·연주자·버전·앨범·길이를 화면에서 비교하고, 파일·분류 버전·캐시 입력을 재확인한 명시적 선택만 참고 근거로 저장한다. 후보 선택은 음악 태그·분류를 바꾸지 않는다.
- 버전 불일치, 다른 연주자, 여러 동등한 후보, 제목만 일치하는 경우에는 외부 연결을 보류한다. 원곡을 커버 파일에 연결하거나 가장 인기 있는 검색 결과를 임의 채택하지 않는다.
- 길이 차이는 후보 검색의 보조 정보이지 같은 녹음이라는 증명이 아니다. 초기 후보 길이 허용값은 §11의 설정을 공유하고 샘플 평가에서 조정한다. 앨범·발매일 차이만으로 동일 녹음을 자동 분리하지도 않는다.
- Last.fm 곡·아티스트 태그는 참고 근거다. 외부 녹음 식별 완료와 동일시하지 않으며, 아티스트 태그를 모든 곡의 정답으로 사용하지 않는다. 불확실한 후보의 태그는 연결 확정된 곡 정보로 LLM에 전달하지 않는다.
- 조회 결과가 없어도 파일 메타데이터 기반 분류·수동 검토를 사용할 수 있다. 미조회·조회 실패·후보 없음·후보 충돌·연결 완료를 구분하고 응답·조회 시점·선택 근거를 캐시한다.
- 캐시는 조회 입력·출처·조회 시점을 기록하고 화면에서 갱신을 요청할 수 있게 한다. 외부 정보 갱신으로 완료 곡의 분류를 자동 재실행하지 않는다. 인증 정보·비밀값은 캐시에서 제외한다.
- MusicBrainz 요청은 작업 전체에 공유된 제한기로 초당 최대 1건과 식별 가능한 User-Agent를 유지한다. 키·연락처가 없거나 사용을 끈 출처는 건너뛰고 빠진 근거를 표시한다. [공식 API](https://musicbrainz.org/doc/MusicBrainz_API).

## 7. LLM 사용 방식


### 7.1 서비스와 모델

- **OpenAI와 Anthropic(Claude)을 지원**하고, GUI 설정에서 서비스별 API 키를 입력한다.
- 1차 분류와 재판정의 서비스·모델을 각각 선택할 수 있게 한다. 설정 화면은 §15를 따른다.
- 아래 모델은 기존에 선택한 초기 기본값이다. OpenAI 기본 모델은 아직 정하지 않았으며, 정답 샘플 평가 후 추천값을 정한다.

| 용도 | 모델 |
|---|---|
| 1차 분류 (전체 곡) | **Claude Haiku 4.5** (`claude-haiku-4-5`) |
| 재판정 (신뢰도 낮은 곡) | **Claude Sonnet 5.5** (`claude-sonnet-5-5`) |

- 정보가 적은 곡은 모델 지식·외부 근거와 미확정 처리 기준이 품질에 영향을 준다. 기존 모델은 초기 선택이며 가격 등급만으로 정확도를 단정하지 않는다. 서비스·모델 추천은 같은 정답 샘플에서 비교한다.
- 코드는 특정 LLM 서비스에 묶이지 않게 만든다. 모델 이름은 설정으로 바꿀 수 있게 한다.

### 7.2 호출 방식

- 한 번에 여러 곡(약 20곡)을 묶어서 요청한다.
- 대량 분류는 선택한 서비스·모델이 지원하는 **Batch API**를 우선 사용한다. 지원 여부와 할인율은 해당 서비스의 공식 문서로 확인한다.
- 태그 목록 등 공통 지시문은 지원 모델의 최소 길이·유효 시간 조건을 충족할 때 **프롬프트 캐싱**으로 재사용한다. 캐시 적중을 비용 계산의 확정 전제로 두지 않는다.
- Claude 새 작업은 공통 지시·분류 목록을 앞쪽 시스템 블록에 고정하고 5분 명시적 캐시를 요청한다. 곡별 입력은 캐시 경계 뒤에 둔다. 최소 토큰 조건은 제공자가 확인하며 적중을 보장하지 않는다. 제출 예약은 모든 입력의 1.25배 쓰기 단가를 상한으로 사용하고 수신한 일반 입력·캐시 읽기·쓰기 사용량으로 정산한다. 이전 작업은 당시 요청 계약을 유지한다.
- 응답은 정해진 JSON 형식(구조화 출력)으로 받는다. 곡마다 신뢰도와 제안 태그를 포함한다.
- 요청·응답은 작업별 곡 참조 ID로 연결한다. 응답 순서에 의존하지 않고 요청 대상 밖 ID·중복 ID·누락·잘린 응답·허용 목록 밖 값·항목 수·대분류/세부 조합을 검증한다. 정상 항목만 저장하고 실패 항목은 별도로 남긴다. JSON 스키마 준수와 곡 판정의 사실 정확성을 구분한다.
- 항목별 상태·값·신뢰도·짧은 판정 근거와 근거 출처를 받는다. 외부 자료에서 확인한 정보와 모델 자체 지식 추정을 구분하고 없는 외부 근거를 만들어 기록하지 않는다. 메타데이터·가사는 곡 자료로 구분해 전달하며 그 안의 문장을 작업 지시나 파일 경로로 실행하지 않는다.
- 근거가 부족한 항목은 "모름"을 허용한다. LLM 분류·재판정 이후에도 미확정 항목이 남으면 §3.8에 따라 별도 보관 대상으로 표시한다. 실제 이동은 적용 단계에서 한다.

### 7.3 정확도 확인

- 개발 초기에 사용자가 직접 정답을 단 **100~200곡 샘플**로 정확도를 측정한다.
- 이 결과로 지시문과 신뢰도 기준값을 조정한다.
- 기본 평가 계획은 200곡이다. 대분류·메타데이터 등급·동명이곡·커버·버전 차이·미확정 사례를 분산해서 고른다. 샘플에 없는 범주는 검증되지 않은 것으로 보고 별도 보완한다.
- 120곡은 지시문·임계값 조정에, 80곡은 최종 검증에 사용한다. 같은 녹음의 복사본은 같은 집합에 둬 정답이 검증 집합으로 새지 않게 한다. 최종 검증 결과를 보고 수정했다면 새 검증 샘플로 다시 평가한다.
- 내가 후보와 정답 초안을 만들되 사용자가 분류 경계와 분위기·컨셉 정답을 검토한다. LLM 답안을 그대로 정답으로 사용하지 않는다. 사용자도 판단할 수 없는 항목은 정답 미확정으로 표시한다.
- 대분류·보컬/연주 정확도, 세부 장르·분위기·컨셉의 다중 태그 정밀도·재현율, 자동 확정 비율과 미확정 비율을 각각 보고한다. 알려진 답을 일부러 전부 미확정 처리해 정확도만 높이는 방식은 평가하지 않는다.
- 초기 목표는 자동 확정한 대분류의 정답률 95% 이상이다. 소규모 샘플 결과를 30만 곡 전체 품질 보증으로 취급하지 않는다. 기준 미달 범주는 자동 확정을 제한하고 근거·모델·지시문을 개선한 뒤 재검증한다.

### 7.5 LLM 전송 정보 범위

- 1차 분류·재판정에는 확보한 제목, 아티스트, 앨범, 발매연도, 곡 길이, 기존 장르 태그, 라이브·리믹스 등 버전 정보와 외부 음악 DB에서 수집한 분류 근거를 전달한다. 없는 값은 만들어 채우지 않는다.
- 기존 장르 태그와 외부 태그는 출처가 있는 참고 근거로 전달한다. 이 값을 최종 분류로 강제하지 않으며 판정은 정해진 분류 목록을 따른다.
- 가사는 기본적으로 전송하지 않는다. 켠 경우 파일의 기존 ID3 가사에서 텍스트를 추출하며 외부 가사를 자동 수집하지 않는다. 가사가 있는 곡 중 미확정·낮은 신뢰도로 재판정하는 단계에만 사용하고, 시간 코드·동기화 표기를 제거한 앞부분 최대 2,000자를 전송한다. 잘린 분량과 전송 내용을 실행 전 확인할 수 있게 한다. 설정을 켜는 것만으로 API 요청을 실행하지 않는다.
- 음악 파일 자체와 앨범 이미지는 전송하지 않는다. 전체 로컬 경로, API 키 등 인증 정보는 LLM 입력·프롬프트에 포함하지 않는다. 인증 정보는 API 연결에만 사용한다.
- 파일명 파싱을 LLM에 맡겨야 하면 폴더 경로를 제외한 파일명만 전달한다. ID3 원본 전체나 외부 응답 원본 전체를 입력에 넣지 않고, 위 범위에 해당하는 곡 정보·분류 근거를 추려 전달한다.
- 전송 범위와 가사 사용 여부는 작업 시작 시점에 기록한다. 작업 전 전송 항목을 확인할 수 있게 하며, 진행 중 작업은 기존 작업 설정을 유지한다 (§15.3).

### 7.6 API 오류·부분 실패와 재시도

- 일시적 오류는 대기 시간을 늘리며 최대 **3회 추가 재시도**한다. 최초 요청을 포함해 최대 4회다. 한도를 넘으면 해당 항목을 실패 상태로 남기고 다른 항목의 완료 결과는 보존한다.
- 재시도 한도는 곡·처리 단계의 논리적 요청 기준으로 관리한다. SDK 내부 재시도와 프로그램 재시도가 겹쳐 한도를 넘지 않게 한다. 구체적 오류 판별·대기 시간·서비스별 요청 제한 대응은 개발 시 공식 API 문서에 맞춰 상세화한다.
- API 키·권한·결제 문제는 같은 요청을 반복하지 않고 해당 API를 사용하는 작업의 신규 요청·재시도를 일시정지한다. 오류 이유와 설정 확인 안내를 표시한다. 다른 서비스의 작업과 로컬 검토를 일괄 중단하지 않는다.
- 부분 성공은 곡별로 구분한다. 정상 응답을 검증해 DB에 저장한 곡은 완료로 유지하고, 실패가 확인된 곡만 재시도한다. 재판정 등 별도 처리 단계는 완료 여부를 별도로 관리한다.
- 전송 후 응답이 끊기는 등 처리 여부가 불확실한 요청은 즉시 재전송하지 않고 `처리 확인 필요` 상태로 보류한다. 조회할 수 있는 작업은 상태·결과를 먼저 확인한다. Batch는 저장한 작업 ID로 조회하고, 확인할 수 없는 요청은 보류 이유를 표시하여 검토한다. 확인 실패 자체를 새 유료 요청의 재전송 근거로 삼지 않는다.
- 실패·처리 확인 필요 상태는 분류 결과의 `미확정`과 구분한다 (§3.8). API 오류만으로 `_미확정` 보관 대상이나 미확정 검토용 재생목록 대상으로 바꾸지 않으며 기존 분류·수동 보호를 유지한다.
- 시도 횟수, 오류 유형, 요청·작업 식별자, 곡별 처리 결과를 DB 작업 이력에 기록한다. API 키 등 비밀값은 기록하지 않는다. 오류 해결 후 작업 재개·취소는 §8.4를 따른다.

### 7.7 분류 실행·재시도·재분류 대상

| 실행 목적 | 대상 규칙 |
|---|---|
| 기본 `분류 실행` | 선택한 작업 범위에서 아직 분류하지 않은 곡만 처리한다. 이미 처리 중·실패·처리 확인 필요인 요청을 새 요청으로 중복 제출하지 않는다 |
| `실패 항목 재시도` | 실패가 확인된 곡·처리 단계만 대상으로 삼고 완료 결과는 보존한다. 오류 유형과 재시도 한도는 §7.6을 따른다 |
| `미확정 재판정` | 사용자가 선택한 범위의 미확정 곡을 다시 판정한다. 1차 작업에서 계획한 재판정의 완료와 별개로 실행 목적을 기록한다 |
| `분류 완료 곡 재분류` | 사용자가 명시적으로 선택했을 때만 실행한다. 이미 완료된 곡을 기본 실행에 자동으로 포함하지 않는다 |

- 각 실행은 §15.6의 `선택한 곡 / 현재 검색·필터 결과 / 라이브러리 전체` 범위와 위 대상 조건을 함께 적용한다. 실제 대상 건수와 추정 비용을 실행 전에 표시한다.
- 모델·분류 목록을 바꾸거나 재스캔하는 것만으로 기존 곡을 자동 재분류하지 않는다. 변경한 설정을 사용하려면 대상과 실행 목적을 선택해 새 작업을 실행한다. 기존 작업의 재개는 시작 시점 설정을 유지한다 (§8.4, §15.3).
- 모든 실행에서 항목별 수동 보호와 충돌 검토 규칙을 유지한다 (§3.9). 재판정·재분류 이전 값과 판정 이력은 보존하며 DB 갱신만으로 파일 적용을 실행하지 않는다.
- 처리 여부가 불확실한 요청은 실패 재시도·미확정 재판정·완료 곡 재분류의 우회 대상으로 사용하지 않는다. 먼저 §7.6의 확인 절차를 따른다.

### 7.8 비용 관리와 제출 계획

- 첫 연결 구현의 내장 단가 표는 공식 자료 확인일을 함께 저장하고 30일이 지나면 제출을 보류한다. 표에 없는 모델은 단가 확인·등록 전 제출하지 않는다. 예약 입력량은 전송할 JSON·지시문·스키마의 UTF-8 바이트 수와 프로토콜 여유분의 보수적 상한으로 계산하며 사용량과 구분한다. 실제 제출 전 API 토큰 계량을 추가하고 더 큰 값으로 예약한다. 모델의 문맥 제한·단가 구간을 벗어나는 요청은 보류한다.
- 구조화 응답의 값을 먼저 검증하고, 수동 보호·현재 입력/판정 버전·대분류/세부 충돌을 다시 검사한다. 잘못된 한 곡의 응답을 다른 곡의 미확정 판정으로 바꾸지 않는다. 응답은 로컬 이력에 보존하고 파일 변경은 하지 않는다.

- 유료 작업마다 USD 예산을 사용자가 입력한다. 기본값은 미설정이며 예산과 가격 정보가 없으면 유료 제출을 시작하지 않는다. 로컬 스캔·수동 검토는 예산 없이 가능하다. 대량 제출과 실제 지출은 설계 위임만으로 승인된 것이 아니다.
- 실행 전 곡 수·묶음 수·1차/재판정 모델·호출 방식·가사 사용·추정 비용·제출 상한을 보여준다. 한 요청은 기본 20곡, 원격 Batch 한 구간은 최대 1,000곡으로 분할한다. 계정 제한이나 예산에 맞춰 더 작게 제출한다. 이 수치는 조정 가능한 초기값이다.
- 정상 예상 비용은 입력 계량과 샘플 출력량으로 계산한다. 별도로 출력 토큰 상한·유효 단가를 사용한 제출 예약 금액을 관리한다. 사고 방지 기준은 `집계 비용 + 미완료 요청의 예약 금액 + 다음 제출 예약 금액`이다. 캐시 적중을 확정 수입처럼 차감하지 않는다.
- 위 금액이 예산의 80%에 도달하면 경고하고 다음 제출로 예산을 넘길 것으로 판단되면 신규 제출·재시도를 멈춘다. 이미 제출된 요청의 비용 차단이나 공급자 청구액의 절대 상한을 보장하지 않는다. 합리적인 상한을 산정할 수 없는 모델·요청은 제출 보류로 표시한다.
- 응답의 사용량에 근거한 비용, 계산상 예약 금액, 아직 사용량을 확인하지 못한 금액을 구분한다. 입력·출력·캐시·과금되는 추론량과 서비스별 차이를 반영한다. 재시도도 별도 요청 비용으로 계산한다. 불확실한 요청의 예약 금액을 임의로 해제하지 않는다.
- 처리 불확실 요청은 요청 ID·원격 ID·예약 금액을 표시한다. 제공자에서 미처리·미과금을 직접 확인했다는 체크와 근거 입력을 모두 받은 경우에만 예약을 해제하고 확인 이력을 남긴다. 과금·처리가 확인되거나 판단할 수 없으면 예약을 유지한다. 해제 후에도 자동 재전송하지 않고 새 계획·명시적 제출을 요구한다.
- 예산을 늘려도 작업을 자동 재개하지 않는다. 가격 정보는 모델·API·유효 날짜·통화·Batch 할인·확인 출처를 포함하며, 오래되거나 직접 입력한 미확인 가격은 표시하고 제출 전 확인한다. 원화는 사용자가 지정한 환율의 참고 표시만 제공한다.
- 결과 캐시의 재사용 조건은 곡 입력·외부 근거·모델·지시문·분류 목록 버전·가사 옵션의 일치다. 같은 제목의 다른 녹음이나 입력이 달라진 곡의 결과를 비용 절감을 위해 재사용하지 않는다.

### 7.9 첫 생성 연결의 검증 범위

- 실행 계획 준비와 실제 제출 버튼을 분리한다. OpenAI Responses와 Claude Messages의 구조화 출력, 입력 계량, 동기 처리와 원격 Batch를 사용한다. 시작 시 제공자·모델·워크스페이스·가격·전송 입력을 저장하며 재개 시 유지한다. 가사는 기본 제외하고 별도 미확정 재판정 작업에서만 선택한다.
- 자동 재판정의 신뢰도 임계값은 정답 샘플 평가 전 활성화하지 않는다. 1차 결과의 미확정 항목은 사용자가 재판정 목적으로 이어 실행할 수 있으며 이미 확정된 항목은 유지한다. 모델의 `confirmed` 결과는 모델 판정이라는 출처를 유지하며 실측 정답률이 확인된 것으로 표시하지 않는다.
- 요청 전 예약, 응답·사용량 저장, 곡별 검증/반영 순서로 기록한다. 응답 수신 뒤 중단하면 저장한 결과만 복구하며 전송 중 중단은 처리 확인 필요로 남긴다. 원격 작업 ID가 있으면 상태·결과를 조회하고 사용량이 확인되지 않은 예약은 유지한다. 원격 취소 요청은 즉시 과금 취소·작업 종료를 의미하지 않는다.
- 정답률·가사 재판정 효과와 실제 Batch 계정 권한/사용량은 별도 실제 검증 대상이다. 테스트 응답과 네트워크를 차단한 SDK 검증을 실제 생성 성공으로 보고하지 않는다.

## 8. DB 개념 설계 (SQLite)

```
tracks      : 내부 파일 ID, 파일 경로, 현재 파일 해시, 제목, 아티스트, 앨범, 길이, 비트레이트, 샘플레이트,
              메타데이터 등급, 대분류, 속성, 처리 상태
artists     : 아티스트 정보 캐시 (참고용 주 장르 등)
tags        : 태그 이름 + 종류(세부장르/분위기/컨셉) + 묶음
track_tags  : 곡-태그 연결 + 출처(LLM/Last.fm/수동) + 신뢰도
suggested   : LLM이 제안한 목록 외 태그
api_cache   : 외부 API 응답 원본
file_ops    : 이름 변경·이동·태그 기록 이력 (되돌리기용)
```

### 8.1 파일 식별

- 처음 등록한 파일에 내부 ID를 부여한다. 이 ID는 프로그램이 파일을 이동·이름 변경·태그 수정해도 유지한다.
- 전체 파일 해시는 내용 변경 확인과 완전히 같은 파일의 후보 검색에 사용한다. ID3 변경으로도 달라지므로 영구 식별자로 사용하지 않는다.
- 프로그램이 태그를 수정하면 변경 전·후 해시를 작업 이력에 기록하고 현재 해시를 갱신한다.
- 같은 곡의 출처·인코딩이 다른 파일에는 각각 ID를 부여하고 중복 후보 관계로 연결한다.
- 내용이 완전히 같은 복사본도 서로 다른 경로에 존재하면 각각 관리한다. 파일 해시에는 유일성 제약을 두지 않는다.
- 프로그램 밖에서 이동·수정한 파일과 같은 해시의 여러 파일, 경로 재사용은 §8.3의 재스캔 규칙으로 처리한다.

### 8.2 파일 변경·복구 기본 원칙

다음 원칙은 확정한 설계 요구사항이다. 구현·복구 검증이 완료되었다는 의미는 아니다.

1. **이동·이름 변경:** 변경 전·후 경로를 기록한다. 되돌릴 경로에 다른 파일이 있으면 덮어쓰지 않고 충돌로 표시한다.
2. **태그 변경:** 수정 전 ID3 데이터를 보관한다. 장르뿐 아니라 보존해야 할 기존 태그도 복구할 수 있어야 한다.
3. **중단 후 재개:** 파일별 완료 상태를 기록하고 실제 파일 상태를 확인한다. 완료한 변경을 반복하지 않으며, 실행 결과가 불확실한 항목은 상태를 확인한 뒤 처리한다.
4. **외부 수정 감지:** 프로그램의 변경 이후 외부에서 수정된 파일은 자동 복원을 멈추고 검토 대상으로 표시한다.

- DB 백업과 음악 파일의 이름·위치·태그 복구는 구분한다. DB만 복원한 상태를 음악 파일 복구 완료로 표시하지 않는다.
- 파일 작업과 DB 기록을 함께 맞추는 복구 절차가 필요하다. 복구 결과의 경로·해시를 DB에 반영한다.
- 원본 저장·파일별 기록·되돌리기의 상세 정책은 다음 절을 따른다. 구현 시 강제 종료·디스크 오류·외부 변경 시나리오를 검증해야 한다.

#### 8.2.1 원본 보관과 파일 변경

- 첫 파일 적용 구현은 ID3v2.3/2.4의 일반 선두 태그에서 TCON 프레임만 바이트 단위로 교체한다. 다른 프레임과 태그 밖 영역을 그대로 보존한다. 확장 헤더·전체 unsynchronisation·footer·알 수 없는 헤더 플래그·과도한 태그 크기는 장르 기록을 보류한다. 이동/이름 변경은 독립적으로 미리볼 수 있다. 지원 배치를 조용히 변환하지 않는다.
- 장르 기록 후 이동 전 중단 상태도 기록한다. 재실행 시 실제 해시가 중간 태그 결과와 맞으면 명시적 재개를 제안하고, 최종 경로·해시가 맞으면 DB 기록만 복구한다. 외부 변경 또는 양쪽 경로 존재는 보류한다.

- ID3 수정 전 원래 ID3 영역의 바이트·배치·버전·길이와 파일 전체 해시를 보존한다. 새로 만들어진 ID3 영역의 제거까지 포함해 원래 파일을 재구성할 수 있어야 한다. 역직렬화한 태그 값만 보관하는 것으로 대체하지 않는다.
- 복구 자료는 사용자 데이터의 `rollback/<파일 ID>/<작업 ID>/`에 두고 무결성 해시·관련 이력을 DB에 연결한다. ID3 외 영역의 바이트가 보존되는지 함께 확인한다. MP3·태그 배치를 안전하게 판별·복구할 수 없는 파일은 첫 버전에서 태그 기록을 보류하고 이유를 보여준다.
- 태그 기록은 같은 볼륨의 임시 복사본에 먼저 수행한다. 기존 장르 이외의 정보·PRIV·가사·커버 보존과 ID3 외 영역의 바이트 일치를 확인한 뒤 원본 경로를 교체한다. 인코딩·음량을 변경하지 않는다. ID3 버전은 가능한 한 유지하고 묵시적으로 일괄 변환하지 않는다.
- 파일별 작업은 변경 전 조건·예정 경로·원본 백업을 먼저 저장한 `준비됨`, 파일 변경을 확인한 `파일 완료`, 현재 해시·경로·결과를 DB에 반영한 `기록 완료` 단계로 남긴다. 파일 시스템과 DB가 하나의 원자적 트랜잭션이라고 가정하지 않는다.
- 각 단계의 안전한 중단 지점에서 진행 상태를 저장한다. 재개 시 실제 전·후 경로와 해시를 대조한다. 파일 변경은 끝났지만 DB 기록이 없으면 기록을 복구하고, 상태가 모호하면 재실행을 보류한다. 임시 파일은 복구·원본 존재를 확인하기 전 제거하지 않는다.
- 첫 버전의 음악 이동은 등록한 음악 루트 안에서 같은 볼륨을 대상으로 한다 (§12.1). 서로 다른 볼륨으로 음악을 이관하는 기능은 후속 범위이며 복사 후 원본 제거를 첫 버전에 숨겨 넣지 않는다.
- 원본 복구 자료와 파일 작업 이력에는 자동 만료를 두지 않는다. 기본 복구 저장 한도는 10GiB이며 80%에 경고한다. 다음 보관으로 한도를 넘으면 새 태그 기록을 보류한다. 사용자가 보관 한도를 늘리거나 복구 가능 범위를 확인한 뒤 자료 정리를 명시적으로 선택해야 한다.
- DB 백업은 기본 하루 첫 파일 적용과 DB 버전 변경 전, 그리고 사용자의 수동 요청에 생성한다. 최근 자동 DB 백업 7개를 유지하되 보관 교체는 정상 새 백업의 검증 후 수행한다. 수동 백업·원본 ID3 자료는 자동 정리하지 않는다. 음악 파일이 없는 DB 백업만으로 파일 복구를 보장하지 않는다.
- 실행 중 DB는 SQLite 백업 기능으로 일관된 사본을 만들고 무결성을 확인한다. 활성 DB 파일만 단순 복사하는 방식은 사용하지 않는다. [SQLite Backup API](https://sqlite.org/backup.html).

#### 8.2.2 되돌리기 범위와 충돌

- 사용자는 파일 또는 적용 작업을 골라 복구 미리보기를 연다. 기본 복구 대상은 해당 파일의 가장 최근 적용이며 이전 작업으로 되돌리려면 이후 작업을 역순으로 함께 되돌릴 범위를 표시한다.
- 이동·이름·태그 등 한 적용에서 여러 변경을 했으면 저장된 실행 순서의 역순으로 복구한다. 선택한 작업에 의존하는 후속 작업을 건너뛰어 예전 경로·해시를 덮어쓰지 않는다.
- 현재 경로·해시가 마지막 적용 결과와 일치하고 복구 자료가 정상일 때만 자동 복구한다. 원래 위치의 다른 파일, 외부 수정, 파일 누락, 복구 자료 손상은 충돌·복구 보류로 표시하고 덮어쓰지 않는다.
- 원래 경로 복원과 태그 복원 후 해시를 대조해 DB의 현재 경로·해시를 갱신한다. 최종 상태 검증 전에는 복구 완료로 표시하지 않는다. 실패한 부분과 아직 복구되지 않은 파일을 따로 남긴다.
- 파일 적용 되돌리기는 분류 판정 이력을 지우지 않는다. DB의 원하는 분류와 실제 파일 배치·태그가 다르면 적용 대기로 표시한다. DB 전체 복원은 작업을 정지하고 현재 DB도 먼저 백업한 뒤 수행하며 실제 파일 재확인을 거친다.

### 8.3 재스캔 처리

> 확정한 설계 규칙이다. 외부 변경 전의 기록을 보존하고 모호한 연결은 검토하도록 한다. 구현·검증은 개발 단계에서 진행한다.

| 확인된 상황 | 처리 규칙 |
|---|---|
| 기존 경로에 현재 해시와 같은 파일이 있음 | 내부 ID와 장르·분위기·컨셉 및 수동 수정 기록을 유지 |
| 기존 경로의 파일이 없고, 새 경로 파일이 기존 현재 해시와 1:1로 일치 | 이동·이름 변경으로 간주해 기존 ID의 경로를 갱신. 동일 내용이라는 근거를 기록 |
| 기존 파일이 남아 있고, 새 경로에 해시가 같은 파일이 추가됨 | 별도 ID로 등록하고 완전히 같은 내용의 파일 관계로 연결 |
| 기존 경로의 파일 해시가 달라짐 | 외부 변경 상태로 표시. 기존 ID·판정·해시 이력은 보존하고, 단순 태그 수정인지 파일 교체인지 검토 전에는 확정하지 않음 |
| 해시가 같은 기존 누락 파일·새 파일이 여러 개여서 연결이 모호함 | 자동 연결을 보류하고 검토 후보로 표시 |
| 정상적으로 완료한 스캔 범위에서 기존 파일이 발견되지 않음 | DB 기록을 보존하고 파일 누락 상태로 표시. 파일 적용·재생목록 생성 대상에서 제외 |
| 드라이브 연결 해제, 접근 거부, 스캔 오류·중단 | 해당 범위는 확인 불가로 표시. 스캔하지 못한 파일을 누락으로 확정하지 않음 |

- 경로·전체 파일 해시만으로 외부 이동과 '같은 파일을 복사한 뒤 원본을 없앤 경우'를 구별할 수 있다고 가정하지 않는다. 1:1 해시 연결은 내용이 동일한 파일로 기존 관리 기록을 이어가는 운영 규칙이다.
- 일부 폴더만 스캔했을 때는 정상적으로 확인한 범위 안에서만 누락을 판정한다. 스캔이 완료되지 않은 범위의 누락 판정은 보류한다.
- 외부 변경·연결 보류 파일은 원래/현재 경로·해시·태그 차이를 비교해 보여준다. 사용자가 기존 파일의 변경으로 연결하거나 새 파일로 등록하도록 선택하고 수동 판정의 승계 여부를 명시한다. 선택 이력과 근거를 보존하며 이전 값을 새 내용에 묵시적으로 적용하지 않는다.
- 연결 보류의 직접 검토에서는 같은 해시의 누락·확인 불가 기록을 후보로 제공한다. 사용자가 하나를 선택하고 기존 분류·수동 보호의 유지 또는 초기화를 명시한다. 저장 직전에 새 파일의 전체 해시와 DB 버전을 대조하고 기존 경로가 실제로 없음을 확인한다. 기존 파일이 존재하거나 접근 실패로 부재를 확인하지 못하면 승계를 막는다. 연결 시 기존 내부 ID를 유지하고 임시 신규 기록을 이력으로 보존하며, 새 파일 선택 시 신규 ID만 사용 가능 상태로 전환한다. 이 선택은 음악 파일을 바꾸지 않는다.
- 외부 변경을 검토하기 전에는 이전 판정을 새 내용에 확정 적용하지 않는다. 해당 파일의 정리·되돌리기·재생목록 포함을 보류한다.
- 재스캔만으로 유료 LLM 재분류를 시작하지 않는다. 재분류 대상과 비용을 별도로 보여주고 분류 실행을 요청받는다.
- 첫 버전 기본 스캔은 전체 파일 SHA-256을 계산한다. 크기·수정 시각이 같다는 이유만으로 내용 일치를 확정하지 않는다. 같은 경로·크기·시각이 유지되면 태그 재파싱은 생략할 수 있으나 해시는 대조한다. 파일 적용 직전에는 다시 해시·경로·접근 가능 상태를 확인한다.
- 스캔은 백그라운드에서 제한된 수의 파일을 순차 읽으며 기본 디스크 읽기 동시성은 1이다. 신규·변경 의심 파일을 먼저 처리하고 현재 선택한 폴더 범위를 분명히 표시한다. 전체 라이브러리 스캔의 읽기 시간은 숨기지 않는다.
- 읽기 전·후 파일 크기·수정 시각과 열린 파일의 상태를 비교한다. 읽는 동안 변경됐거나 잠김·읽기 오류가 있으면 이번 스캔에서 확정하지 않고 재확인 대기로 둔다. 정상 해시를 얻지 못한 범위에 누락 판정을 실행하지 않는다.
- 스캔이 끝날 때 선택 범위·성공 범위·실패 범위·발견 ID를 기록하고 정상 완료 범위에 한해 누락을 판정한다. 빠른 목록 조사와 전체 내용 검증을 같은 완료 상태로 표시하지 않는다. 향후 증분 스캔 최적화도 §8.3의 식별 신뢰도를 낮추지 않아야 한다.

### 8.4 작업 일시정지·재개·취소와 앱 종료

- 제어 대상은 사용자가 선택한 작업이다. 작업 종류에 맞는 일시정지·재개·취소 동작을 제공하고 로컬 작업 상태와 이미 제출된 원격 Batch 상태를 구분해 기록·표시한다.
- **일시정지:** 신규 API 요청·재시도·다음 파일 작업을 시작하지 않는다. 진행 중인 파일 변경은 안전한 지점까지 마무리하고 결과·현재 위치를 저장한다. 정지 요청과 정지 완료를 구분하며, 이미 진행 중인 요청의 정상 결과는 보존한다.
- **재개:** 사용자가 재개를 선택하면 완료된 곡·처리 단계는 건너뛰고 남은 항목부터 이어간다. API 처리 여부가 불확실한 요청은 §7.6에 따라 먼저 확인하며, 파일 상태가 불확실한 항목은 §8.2에 따라 확인한다. 재개만으로 재시도 횟수를 초기화하지 않는다.
- **취소:** 아직 시작하지 않은 나머지 작업을 종료한다. 진행 중인 파일 변경은 안전한 지점까지 마무리하고 상태를 기록한다. 완료된 분류와 파일 변경은 유지하며 자동으로 되돌리지 않는다. 파일 복구는 사용자가 작업 이력에서 별도로 요청한다 (§8.2).
- **앱 종료:** 정상 종료에서는 진행 중인 파일 변경을 안전한 지점까지 마무리하고 작업 상태·완료 결과·원격 작업 ID를 저장한다. 강제 종료·비정상 중단 이후에는 저장 기록과 실제 상태를 대조해 복구한다. 재실행 시 이어갈 작업과 확인이 필요한 항목을 보여준다.
- 앱을 다시 열거나 오류 설정을 수정하는 것만으로 새 유료 요청·재시도·파일 변경을 시작하지 않는다. 사용자가 재개를 선택한 뒤 진행한다. 원격 작업의 상태 조회·기제출 결과 수집은 새 분류 요청·파일 적용과 구분한다.
- 로컬 일시정지·취소를 원격 Batch 중단 성공으로 표시하지 않는다. 원격 취소는 서비스 지원 여부를 확인해 별도로 요청하고, 요청 접수와 실제 취소 완료·부분 완료를 구분해 확인한다. 이미 제출된 작업의 결과·비용을 즉시 차단한다고 보장하지 않는다.
- 완료 결과와 뒤늦게 수집한 정상 응답은 작업 이력에 보존한다. 결과 반영은 현재 수동 보호·충돌 검토 규칙을 따르며 (§3.9), 새 요청이나 파일 변경을 자동으로 재개하지 않는다. 파일 변경의 안전한 중단·복구 지점과 원격 취소의 서비스별 상세 방식은 개발 시 검증한다.

### 8.5 작업·상태 데이터와 동시 실행

- DB에는 곡별 분류 항목 상태·수동 보호, 외부 식별 후보와 선택 근거, 분류 이력·규칙 버전, 작업 대상 스냅샷·진행 상태, 요청별 ID·사용량·예약 비용, 백업·복구 자료 연결을 추가한다. 이 표는 개념 설계이며 실제 스키마·마이그레이션은 개발 단계에서 작성한다.
- 작업 대상은 실행 직전 DB 조회로 확정하고 ID 목록 또는 재현 가능한 대상 스냅샷을 저장한다. 진행 중 검색·필터가 바뀌어도 작업 대상이 바뀌지 않는다. 화면의 한 페이지만 저장한 범위로 취급하지 않는다.
- GUI와 스캔·해시·API 작업을 분리하고 DB 쓰기는 한 경로로 직렬화한다. 긴 작업의 진행 이벤트는 묶어서 전달해 목록 갱신으로 화면이 멈추지 않게 한다.
- 같은 파일의 파일 변경·복구 작업은 동시에 실행하지 않는다. 진행 중 API 결과는 입력·판정 버전과 현재 수동 보호를 확인한 뒤 반영한다. 오래된 결과는 이력으로 보존하되 새 입력의 판정을 덮어쓰지 않는다.
- DB 목록 조회는 페이지·지연 로딩으로 수행하고 검색·정렬·집계는 DB가 처리한다. 파일명·제목·아티스트의 정규화 검색값을 인덱싱하며 30만 곡 전체를 GUI 객체로 적재하지 않는다.

## 9. 출력

### 9.1 대상 환경

- PC: 곰오디오
- 폰: 삼성 뮤직
- 폰에는 PC의 음악 폴더를 **통째로 복사**해서 사용한다.
- 출력은 **장르 탐색**과 **m3u 재생목록**을 목표로 한다. 실제 지원·인코딩·경로 호환성은 두 앱에서 검증한다 (§16.3).

### 9.2 mp3 파일 태그

- ID3 장르 필드에는 **대분류만** 기록한다. 대상 앱의 표시 방식은 §16.3에서 확인한다.
- 하나라도 미확정인 분류 항목이 있으면 대분류가 알려져 있어도 ID3 장르를 기록·삭제하지 않고 기존 값을 유지한다. 기존 장르가 없는 파일도 미확정 동안은 새로 채우지 않는다. 알아낸 분류는 DB에 보관한다.
- 모든 분류 항목이 확정된 곡만 장르 기록 대상으로 삼는다. 컨셉을 검토한 결과 해당 태그가 없는 경우는 확정된 상태다 (§3.8). 확정되거나 DB를 수정하는 것만으로 파일을 변경하지 않으며, 미리보기 후 명시적으로 적용한다.
- 세부 장르, 분위기, 컨셉은 파일에 쓰지 않는다.
  태그를 고칠 때마다 파일이 바뀌어 폰으로 다시 복사해야 하기 때문이다.
- 파일 기록은 분류 결과가 안정된 뒤 **한 번에** 한다.
  실제 태그가 바뀐 파일은 폰으로 다시 복사해야 한다.

### 9.3 폴더 구조

음악 파일은 **대분류 폴더**로 나눈다.

```
MUSIC_ROOT/
  가요/
    잔나비 - 주저하는 연인들을 위해.mp3
  트로트/  팝/  재즈/  뉴에이지/  클래식/  CCM/  기타/
  _미분류/        아직 분류하지 않은 곡
  _미확정/        LLM 처리 후에도 미확정 항목이 남아 검토가 필요한 곡
  _중복검토/      §11 참고
  _삭제예정/      §11 참고
  [분위기] 잔잔한.m3u8
  ...
```

- 대분류가 바뀌면 파일도 해당 폴더로 옮긴다. (이동 기록은 `file_ops`에 남긴다)
- LLM 처리 이후 미확정 항목이 남은 곡은 대분류 폴더 배치보다 `_미확정` 보관을 우선한다. 검토 후 미확정을 해결하면 대분류 폴더로 복귀한다. 이동·복귀 모두 미리보기 후 실제 적용한다 (§3.8).
- 중복 검토 중인 후보를 폴더 보관하면 분류 상태와 관계없이 `_중복검토`에 함께 모은다. 보관을 선택하지 않으면 원래 위치의 GUI 비교를 유지하고 후보의 자동 배치를 보류한다. 보관 적용의 우선순위는 `_중복검토 → _미확정 → 대분류 폴더`다. 사용자가 남기지 않기로 선택한 파일의 `_삭제예정` 이동은 별도의 검토 결과다 (§11).
- `_`로 시작하는 폴더는 프로그램이 관리하는 작업 폴더다.

### 9.4 재생목록 (m3u)

m3u는 곡 파일 경로 목록만 담은 텍스트 파일이다. 곡을 복사하지 않고 여러 재생목록에 같은 곡을 넣을 수 있다.

- 세부 장르, 분위기, 컨셉별 재생목록을 생성한다.
- LLM 처리 이후 미확정 항목이 남은 곡은 확정된 태그가 있어도 일반 재생목록(조합 재생목록 포함)에서 제외한다. 별도의 `[검토] 미확정 곡.m3u8`에 모아 청취·검토할 수 있게 한다. 확장자는 선택한 출력 형식을 따른다.
- 검토용 재생목록은 DB의 미확정 상태를 기준으로 생성한다. `_미확정`으로 이동하기 전에도 포함하며, DB의 현재 경로를 사용한다. 파일 누락·확인 불가·외부 변경·연결 보류 등으로 사용이 제한된 파일은 일반 재생목록과 동일하게 제외한다 (§8.3).
- 미확정이 해결된 곡은 다음 재생목록 생성 시 검토용 목록에서 빠지고 확정된 태그에 맞는 일반 목록에 포함된다. 기존 m3u 갱신은 재생목록 생성 작업에서 수행한다.
- m3u는 음악 폴더 최상위에 두고 **상대 경로**를 쓴다. 폴더째 복사해도 동작한다.
  - 예: `가요/잔나비 - 주저하는 연인들을 위해.mp3`
  - 경로 구분자는 PC와 폰 모두에서 동작하도록 `/`를 쓴다. (앱 테스트로 확인 필요)
- m3u는 항상 DB에서 새로 생성한다. 파일이 이동해도 경로가 자동으로 맞춰진다.
- 기본 파일 이름 예: `[장르] 재즈 - 보사노바.m3u8`, `[분위기] 잔잔한.m3u8`, `[컨셉] 크리스마스.m3u8`, `[CCM] 연주.m3u8`
- 조합 재생목록(예: 가요 + 잔잔한 + 비오는날)은 모든 조합을 미리 만들지 않고, 필요할 때 DB에서 생성한다.
- 기본 출력은 UTF-8·CRLF·상대 경로의 **`.m3u8`**이며 설정의 파일 정리·재생목록에서 기존 앱용 UTF-8 `.m3u`를 선택할 수 있다. 실제 곰오디오에서 `.m3u`는 BOM 유무에 관계없이 한글 경로를 잘못 읽었으며 `.m3u8`은 복사된 음악 폴더의 상대 경로·`/`·한글·장르와 재생을 확인했다. 삼성 뮤직은 장치 검증 전이며 지원을 주장하지 않는다.
- 형식 변경만으로 기존 목록을 삭제하거나 확장자를 바꾸지 않는다. 다음 명시적 생성에서 선택 형식의 새 목록을 만들고, 프로그램 소유 목록도 같은 확장자의 출력만 재사용한다. 다른 형식에 저장된 조합 정의는 이름별 최신 값으로 중복 없이 가져온다.
- 재생목록에는 파일의 현재 적용 경로를 사용한다. `_삭제예정`과 아직 결론이 나지 않은 중복 후보는 일반 재생목록에서 제외한다. 중복 후보는 검토용 목록에서 비교하고 미확정 후보의 검토용 목록 포함은 §3.8을 유지한다.
- 프로그램이 생성한 목록 경로·종류·갱신 시점을 기록하고 해당 목록만 갱신한다. 같은 이름의 사용자 목록이 있으면 새 출력 이름을 제안한다. 음악 파일 적용·복구로 경로가 바뀌면 목록을 갱신 필요로 표시하고 별도 생성 작업에서 갱신한다. 부분 작업 실패 뒤에는 확인된 현재 경로만 내보낸다.

## 10. 파일 이름 정리

- 형식: `아티스트 - 제목.mp3`
- 모든 변경을 `file_ops`에 기록해서 되돌릴 수 있게 한다.
- Windows 파일 이름 제약을 처리한다.
  - 사용할 수 없는 문자(`\ / : * ? " < > |`)는 비슷한 문자로 바꾼다.
  - 같은 이름이 이미 있으면 안정된 파일 ID 접미사로 구분한다.
  - 경로가 매우 긴 경우도 처리한다.
- **한글 자모 정규화(NFC)**: 맥에서 온 파일 이름은 한글이 자모 단위로 분리(NFD)되어 있을 수 있다.
  이름 비교와 저장 전에 항상 NFC로 정규화한다. 이렇게 하지 않으면 같은 이름이 다르게 인식된다.
- 같은 제목·아티스트라도 라이브·리믹스 등 식별된 버전 표시를 이름에 보존한다. 충돌 시 안정된 짧은 파일 ID 접미사를 붙이고 Windows의 대소문자 비구분 충돌·예약 이름·끝 공백·끝 마침표도 확인한다. 같은 파일에 다시 미리보기를 실행해도 불필요한 새 이름을 만들지 않는다.
- 첫 버전은 루트 아래 경로 길이를 보수적으로 계획하고 긴 경우 제목을 줄인 후보와 파일 ID를 미리보기로 보여준다. 전체 경로가 처리 환경의 한도를 넘으면 적용을 보류한다. 개인 음악 루트의 실제 길이는 설정 시 검사한다.
- 등록 루트·원본·목적지는 실제 절대 경로로 확인한다. 루트 밖으로 벗어나는 경로와 다른 볼륨은 첫 버전에서 거부한다. 정션·심볼릭 링크의 외부 경로를 묵시적으로 따라가지 않는다.

## 11. 중복 곡 처리

오디오 분석을 하지 않으므로 **"아티스트와 제목이 같고 길이가 비슷하면 중복 후보"**로 잡는다.
최종 판단은 **사용자가 직접 듣고** 한다.

```
_중복검토/
  잔나비 - 주저하는 연인들을 위해/
    [추천] 320k 44.1kHz 멜론 - 잔나비-08-주저하는 연인들을 위해.mp3
    320k 48kHz - 잔나비 - 주저하는 연인들을 위해.mp3
```

1. GUI에서 원래 위치의 후보를 비교한다. 폴더로 모아 듣고 싶으면 보관 적용으로 곡별 하위 폴더에 모은다.
2. GUI에는 음질 정보와 추천 이유를 표시한다. 보관 방식에서는 미리보기 후 파일 이름에도 이를 붙일 수 있다.
3. 남길 파일을 하나 이상 명시적으로 선택한다. 선택한 파일은 원래 자리로 돌아가되 LLM 처리 후 미확정·분류 확정 파일은 아래 규칙에 따라 배치한다. 남기지 않기로 명시한 파일만 `_삭제예정/` 이동 계획에 넣는다. 서로 다른 녹음·판단 보류는 §11.1을 따른다.
4. 사용자가 직접 삭제하거나 중복 비교의 명시적 휴지통 이동을 사용한다 (§11.2).

- 중복 폴더 보관을 적용하면 미확정인 파일도 후보끼리 비교할 수 있도록 `_중복검토/곡명/`에 함께 모은다. 물리적 위치와 별개로 DB의 미확정 상태는 유지한다.
- 중복 검토 후 남길 파일이 LLM 처리 이후에도 미확정이면 `_미확정/`으로 보낸다. 모든 분류 항목이 확정된 파일은 해당 대분류 폴더로 보낸다. 중복 검토가 끝나기 전에 분류만 확정된 경우에는 후보와 함께 유지한다.
- 후보 보관과 검토 결과에 따른 이동·복귀·이름 변경 모두 미리보기 후 명시적으로 적용하고 `file_ops`에 기록한다. GUI에서 선택하는 것만으로 파일을 이동하지 않는다.
- 미확정 파일의 일반 재생목록 제외·검토용 목록 포함과 기존 ID3 장르 유지 정책은 `_중복검토`에 있는 동안에도 동일하게 적용한다 (§9.2, §9.4).

**추천 기준** (비트레이트 숫자만으로는 판단하지 않는다. 저음질을 320k로 재변환한 파일이 있을 수 있다.)

1. 출처 신뢰도 (멜론 등 정식 다운로드 태그 우선)
2. 비트레이트, 샘플레이트
3. 메타데이터 완성도

### 11.1 후보 생성과 GUI 청취·선택

- 첫 후보 기준은 정규화된 아티스트·제목·버전과 길이 차이 최대 3초다. 길이 기준은 설정에 노출하며 개발 초기의 진짜/가짜 중복 샘플로 조정한다. 해시 완전 일치는 별도 표시하지만 자동으로 남길 파일을 고르지 않는다.
- 라이브·리믹스·다른 연주자 등 버전이 다르면 일반 중복 후보에서 분리한다. 아티스트·제목 인덱스 안에서 후보를 검색해 전체 파일의 모든 조합을 비교하지 않는다. 후보 관계를 곡 파일 ID 사이에 보존한다.
- GUI의 기본 청취는 원래 위치에서 수행한다. `_중복검토`에 모으는 기존 보관 방식도 유지하되 별도 미리보기·적용으로 제공한다. GUI 비교를 열었다고 자동 이동·이름 변경하지 않는다.
- 보관하지 않은 미해결 후보는 위치 변경을 보류한다. 보관 적용은 그룹의 모든 사용 가능한 후보를 함께 계획하며 일부 후보만 이동 가능한 경우 이유를 표시하고 그룹 보관을 보류한다. 검토 완료 후 남길 파일의 정상·미확정 배치는 물리적 보관 여부와 관계없이 미리보기·적용한다.
- 비교 표에는 파일 경로·길이·출처·비트레이트·샘플레이트·메타데이터 완성도·버전과 추천 이유를 표시한다. 파일명을 아직 바꾸지 않았어도 같은 정보를 볼 수 있어야 한다.
- `재생 / 일시정지 / 위치 이동 / A↔B 전환 / 볼륨`을 제공한다. A↔B 전환은 가능한 같은 재생 위치에서 듣되 곡의 완전한 시간 정렬을 보장하지 않는다. 파형·음향 지문·자동 음질 분석은 추가하지 않는다.
- 사용자는 `이 파일 유지 / 여러 파일 유지 / 서로 다른 녹음 / 판단 보류`를 선택한다. 추천은 참고이고 기본 선택은 없다. 남기지 않기로 **명시한** 파일만 `_삭제예정` 이동 계획에 넣으며 판단 보류 그룹은 그대로 유지한다.
- 내장 청취는 Qt Multimedia의 QMediaPlayer·QAudioOutput으로 구성하고 파일 변경 전에 재생 핸들을 해제한다. 재생 실패 시 오류와 `기본 음악 앱으로 열기`를 제공한다. 실제 MP3 재생·배포 백엔드는 Windows 검증 대상이다. [Qt 공식 플레이어](https://doc.qt.io/qtforpython-6/PySide6/QtMultimedia/QMediaPlayer.html).

### 11.2 중복 비교의 선택 파일 삭제

- `유지` 체크박스와 삭제 대상을 분리한다. 표의 행 선택(Ctrl/Shift로 여러 행) 뒤 `선택 파일 삭제 · 휴지통`으로 파일 이름·전체 경로·개수와 남길 개수를 확인한다. 취소가 기본이며 그룹에서 한 개 이상 남겨야 하고 유지 체크된 파일은 삭제 대상으로 허용하지 않는다.
- Windows IFileOperation의 휴지통 전용 플래그와 삭제 전 콜백으로 영구 삭제를 차단한다. 휴지통을 사용할 수 없거나 파일이 잠겼으면 보류하며 영구 삭제로 대체하지 않는다. 네트워크·정션·링크·루트 밖 경로는 지원하지 않는다.
- 실행 전에 전체 후보의 실제 내용 해시·경로·DB revision/상태를 재확인한다. 스캔·미완료 파일 작업·미완료 분류 대상과 충돌하면 보류한다. 확인 이후 변경된 후보는 다시 검토해야 한다. 재생 핸들을 해제하고 백그라운드에서 실행하며 실행 중 창 종료/다른 검토 동작을 잠근다.
- DB 백업 후 작업 이력과 대상별 전송 전/성공/실패/처리 확인 필요 기록을 보존한다. 실제 휴지통 이동이 확인된 파일은 DB에서 누락으로 표시하고 기존 ID·판정·수동 보호를 보존한다. 일부 실패는 성공 건과 따로 표시하며 중단·결과 불확실 대상을 자동 재삭제하지 않는다.
- Windows 휴지통에서 복원한 뒤 폴더 스캔으로 같은 경로·내용의 기존 ID를 다시 사용할 수 있다. 이 작업은 앱 파일 정리의 되돌리기와 구분한다. 검증은 별도 사본에서 하고 실제 사용자 라이브러리에는 테스트 삭제를 적용하지 않는다.

### 12.1 배포와 데이터 위치

- 첫 버전은 설치 프로그램·자동 업데이트 없이 실행 파일과 의존 라이브러리를 담은 ZIP으로 배포한다. 단일 EXE보다 문제 원인과 멀티미디어 의존성을 확인하기 쉬운 폴더형으로 시작한다. 사용자는 Python을 별도 설치하지 않아도 실행되는 것을 완료 조건으로 둔다.
- 패키징 도구는 `pyside6-deploy`의 `standalone` 모드를 사용한다. Windows 11 x64·Python 3.13 조합으로 빌드하고 별도 Windows 환경에서 Qt 플러그인·MP3 재생을 검증한다. 도구 설치·빌드·코드 작성은 "개발 시작" 이후 수행한다. [Qt 배포 도구](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html).
- 배포 경로는 `dist/main.exe`로 고정하고 DLL·리소스·고지는 `dist` 바로 아래에 함께 둔다. 버전별 배포 폴더를 만들지 않는다. 앱 버전·Git 커밋·빌드 시각은 `dist/build-info.json`과 앱 내부 버전, Git 이력으로 관리한다. 컴파일은 `build`의 임시 폴더에서 수행하고 빌드·고지 작성 성공 후 출력 폴더를 통째로 교체한다. 실행 중인 배포는 교체하지 않으며 교체/바로가기 갱신 실패 시 기존 배포로 되돌린다. 교체 전 배포는 `build`의 내부 복구 폴더에 보존한다.
- 프로젝트 루트의 `music-sorter.lnk`를 고정 실행 진입점으로 제공한다. 성공한 배포의 `main.exe`를 가리키도록 바로가기를 교체한다. `--output-dir`은 지정한 폴더 바로 아래를 출력 위치로 사용한다. 실패·dry-run에서는 기존 배포와 바로가기를 유지한다. `--shortcut-only`로 기존 빌드에 연결할 수 있다. 바로가기는 Git에서 제외하며 프로젝트를 이동하면 다시 생성한다.
- 일반 사용자 데이터는 `%LOCALAPPDATA%/music-sorter/`에 둔다. 일반 설정·DB·캐시·로그·DB 백업·ID3 복구 자료를 하위 영역으로 분리한다. 실제 개인 경로는 로컬 설정에만 보관한다. 실행 파일 폴더 교체로 데이터가 지워지지 않게 한다.
- 여기서 포터블은 설치 없이 실행할 수 있다는 뜻이다. API 키·DB까지 ZIP과 함께 다른 PC로 자동 이전하는 뜻은 아니다. 새 PC에서는 키를 다시 등록하고 DB·자료 이관을 명시적으로 수행해야 한다.
- 첫 버전은 한 라이브러리·하나의 음악 루트와 그 하위 MP3를 관리한다. 음악 폴더째 폰에 복사하는 상대 경로 출력을 안정화한다. 여러 루트·여러 사용자·서로 다른 볼륨의 통합 라이브러리는 후속 범위로 둔다.
- DB 위치는 처음 생성할 때 선택할 수 있다. 이후 변경은 작업을 정지하고 DB·복구 자료를 검증된 사본으로 이관하는 절차로 제공하며 경로 칸만 바꿔 연결하지 않는다. 실행 중 DB는 로컬 디스크를 기본으로 하며 동시 실행·동기화 폴더의 활성 DB 공유를 첫 버전에서 지원하지 않는다.
- 업데이트는 새 프로그램 폴더로 교체한다. DB 스키마 변경 전 백업·호환성 확인을 수행하고 실패하면 기존 데이터에 새 작업을 시작하지 않는다. 이전 프로그램이 새 스키마를 임의로 열지 않게 한다. 배포에는 사용한 의존성·라이선스 고지·버전을 포함하고 배포 구성에 맞는 요건을 검증한다.
- ffprobe는 로컬 메타데이터 확인을 위한 선택적 도구로 경로를 설정한다. 시스템의 특정 개인 경로를 코드에 넣지 않는다. 없을 때도 가능한 mutagen 스캔은 제공하고 부족한 정보·기능만 표시한다. 외부 ffmpeg 전체를 자동 설치하지 않는다.

- API 연결 확인·샘플 분류·원본 자료 정리·DB 이관은 설정값 저장과 별도의 작업 버튼이다. 각 작업의 실제 대상·효과를 보여주며 개인정보 없는 설정 내보내기는 키·연락처·음악 경로를 제외한다.

### 15.3 LLM 설정 동작

- **연결 등록과 사용 모델 선택을 분리**한다. 두 서비스의 키를 저장해 두고, 1차·재판정은 각기 다른 서비스를 선택할 수 있다.
- 키 입력칸은 기본 마스킹한다. 연결 상태는 미등록 / 등록됨·미확인 / 연결 확인됨 / 오류로 구분하고 마지막 확인 시점을 표시한다.
- `연결 확인`은 인증·모델 목록 조회를 사용한다. 조회 성공만으로 특정 모델의 분류·과금 권한까지 확인됐다고 표시하지 않는다.
- 연결 확인은 버튼을 눌렀을 때만 공식 HTTPS 모델 목록 API에 GET 요청을 보낸다. 자동 재시도·리디렉션·생성 요청은 하지 않는다. 백그라운드 조회 중 키 변경과 설정 창 종료를 막고, 요청별 통신 대기 10초·전체 조회 예산 30초·최대 10페이지로 제한한다. 30초는 페이지/수신 구간 사이에서 확인하며 DNS·진행 중 통신에 따라 실제 종료 시각은 초과할 수 있다. 실패는 인증/권한/워크스페이스/요청 제한/서버/통신/응답 오류로 구분하며 키·응답 원문을 로그나 화면에 노출하지 않는다.
- Claude의 여러 워크스페이스용 키는 API 연결 메뉴에서 워크스페이스 ID를 지정한다. 빈 값이면 헤더를 생략하며 이 값은 일반 설정으로 저장한다. 공식 근거: [Claude 인증](https://platform.claude.com/docs/en/manage-claude/authentication), [Claude 모델 목록](https://platform.claude.com/docs/en/api/http/models/list), [OpenAI 모델 목록](https://developers.openai.com/api/reference/resources/models/methods/list).
- 확인 결과·시각·조회 모델은 현재 설정 창에서만 유지한다. 키 교체/삭제·Claude 워크스페이스 변경·재조회 실패 때 해당 목록과 성공 표시를 무효화한다. 다시 창을 열면 미확인으로 시작한다. 모델 목록을 갱신해도 입력된 모델 ID는 자동으로 바꾸지 않는다.
- `샘플 분류 테스트`는 별도 버튼으로 제공하며, 전송 정보와 비용 발생 가능성을 보여준 뒤 사용자가 실행한다.
- 모델 목록 조회와 직접 모델 ID 입력을 지원한다. 목록 조회만으로 구조화 출력·Batch 지원을 알 수 있다고 가정하지 않는다. 기능 정보와 테스트 결과를 별도로 관리한다.
- 선택 모델이 지원하지 않는 옵션은 이유를 표시하고 사용하지 못하게 한다. 서비스·모델 자동 대체는 기본적으로 하지 않는다.
- 새 설정은 새 작업에 적용한다. 진행 중 작업은 시작 시점의 서비스·모델·분류 규칙을 기록해 유지한다.
- 대량 작업 제출 전 대상 곡 수, 서비스·모델, 호출 방식, 추정 비용을 작업 화면에 표시한다. 비용은 추정치이며 계정 잔액이나 청구 금액으로 표현하지 않는다.
- 예산 기준에 도달하면 추가 요청·Batch 제출을 중단한다. 이미 제출된 요청 비용까지 즉시 차단된다고 보장하지 않는다.
- 프로그램을 닫아도 이미 제출한 원격 Batch는 계속 처리될 수 있다. 재실행 시 작업 ID로 상태 확인·결과 수집을 재개하도록 설계한다.
- 일시정지·취소·재개·앱 종료 시 확정한 작업 제어 규칙은 §8.4를 따른다. 재실행의 원격 상태 확인·결과 수집을 신규 유료 요청이나 파일 적용의 자동 재개로 취급하지 않는다.

### 15.4 설정 저장과 우선순위

- GUI에 입력한 OpenAI·Anthropic·Last.fm API 키는 `keyring`의 Windows 자격 증명 저장소에 저장한다. 서비스·계정 프로필별 참조만 일반 설정에 둔다. Windows용 백엔드 지원은 [keyring 공식 문서](https://keyring.readthedocs.io/en/stable/)로 확인했으며 실제 등록·조회·삭제는 개발 단계에서 검증한다.
- 자격 증명 저장소를 사용할 수 없으면 오류를 보여주고 저장을 보류한다. 평문 파일·일반 DB로 자동 대체하지 않는다. 필요한 경우 사용자가 선택한 세션 한정 키 입력을 제공하고 앱 종료 때 제거한다.
- 일반 설정은 사용자 앱 데이터의 `settings.json`에 저장한다. 음악 경로·연락처는 여기에 둘 수 있으나 저장소·진단 로그·공유용 내보내기에 포함하지 않는다. API 키는 DB·로그·백업·내보내기에 넣지 않는다.
- 평상시 GUI는 `.env`를 자동 탐색·읽기·수정하지 않는다. `.env.example`은 설정 항목 목록과 개발용 입력 예시이며 `.env`는 사용자가 명시적으로 선택한 개발 프로필에서만 읽는다. 환경 변수도 같은 개발 프로필에서만 적용하고 활성 소스를 표시한다.
- 일반 값의 우선순위는 `기본값 < GUI 사용자 설정 < 명시적 개발 프로필(.env < 프로세스 환경 변수) < 실행 화면에서 선택한 해당 작업 옵션`이다. 기본 GUI의 키는 자격 증명 저장소, 개발 프로필의 키는 명시적으로 선택한 `.env`·환경 변수에서 가져온다. 소스 간 키를 묵시적으로 섞거나 다른 서비스로 대체하지 않는다.
- 기존 `.env`를 가져올 때 사용자에게 키·일반 값 목록을 보여주고 키는 자격 증명 저장소로, 일반 값은 로컬 설정으로 이관한다. 가져왔다는 이유로 원본 `.env`를 삭제하지 않는다. 설정 예시의 상대 경로는 명시적으로 선택한 `.env`의 폴더를 기준으로 해석한다.
- 작업 시작 시 모델·규칙·전송 옵션·예산·일반 설정과 자격 증명 참조를 기록한다. 실제 비밀값은 스냅샷에 넣지 않는다. 키 교체·삭제로 기존 작업을 계속할 수 없으면 일시정지하며 재개 시 같은 서비스의 새 등록 키를 사용한다.
- API 키가 없어도 로컬 스캔·목록 검토·수동 분류·중복 청취·기존 결과 내보내기를 제공한다. 연결 정보·설정값 저장만으로 분류를 시작하지 않는다.

**데이터 관리 구현 절차**

- DB 복원은 선택 사본의 무결성·스키마·음악 루트와 곡 수를 검증하고 로컬 준비 사본을 만든 뒤 확인한다. 현재 DB의 검증된 백업을 남기고 교체한다. 미완료 파일 저널이나 전송/원격/사용량 미확인 요청이 있으면 복원을 보류하여 복구·비용 기록을 잃지 않는다. 복원 뒤 파일 상태를 재스캔 필요로 표시하고 음악 파일은 변경하지 않는다.
- 데이터 위치 이관은 비어 있는 로컬 목적지에 일관된 DB·일반 설정·복구 자료를 복사하고 전체 해시를 확인한다. DB 안의 원본 ID3 보관 경로를 새 사본으로 바꾸고 기존 자료를 보존한다. 활성 위치 전환과 재실행은 검증된 사본의 경로를 확인한 뒤 수행한다.
- 공유용 설정 내보내기는 등록 키뿐 아니라 음악 경로·연락처·워크스페이스 식별자를 제외한다. 데이터 관리 화면의 캐시/이력 현황도 키나 원문 API 오류를 표시하지 않는다.

### 15.5 플랫폼 검토 근거 (2026-10-06)

### 15.6 메인 화면·작업 흐름

> 기본 구성·작업 흐름·스타일 명세를 채택했다. 실제 GUI 렌더·DPI·조작 검증은 개발 단계에 수행한다.

- 왼쪽 탐색 메뉴: `음악 라이브러리 / 분류 확인 / 중복 곡 확인 / 재생목록 / 작업 기록`.
- 라이브러리 화면 상단: §15.9의 6단계 작업 영역과 다음 행동 안내, 검색·장르·분위기·컨셉·처리 상태 필터. 통계는 작게 표시하고 작은 창에서는 설명·통계를 접어 목록 공간을 확보한다.
- 중앙 곡 목록: 선택, 제목, 아티스트, 대분류, 세부 장르, 보컬/연주, 검토 여부·처리 상태. 음질·경로 등 보조 열은 필요 시 표시한다.
- 오른쪽 곡 상세: 선택한 곡의 메타데이터, 분류 결과, 출처·판정 근거, 미확정 항목, 수동 수정.
- 수동 분류는 항목별 보호 상태와 `자동 분류로 되돌리기` 동작을 표시한다 (§3.9).
- 수동 보호와 충돌해 보류한 자동 변경은 기존 값·제안 값·충돌 이유를 비교해 보여주고 검토할 수 있게 한다 (§3.9).
- 하단 작업 상태: 단계, 처리 건수, 대기·실패 건수, 비용 추정/집계, 일시정지·재개 등 작업 종류에 맞는 제어. 세부 진행은 작업 이력에서 확인한다.
- 정지 요청/정지 완료, 로컬 취소/원격 취소 요청/원격 취소 결과를 구분해 표시하며, 재실행 시 이어갈 작업을 안내한다 (§8.4).
- 실행 범위는 `선택한 곡 / 현재 검색·필터 결과 / 라이브러리 전체`를 명시적으로 구분하고 대상 건수를 보여준다. 현재 화면에 불러온 페이지를 필터 결과 전체로 오인하지 않게 한다.
- 실행 목적은 `분류 실행 / 실패 항목 재시도 / 미확정 재판정 / 분류 완료 곡 재분류`로 구분하고, 작업 범위 안에서 실제 조건에 맞는 대상 건수와 추정 비용을 보여준다 (§7.7).
- 기본 사용 흐름: `폴더 등록 → 스캔 → 외부 정보 조회·분류 → 검토·수정 → 파일 정리 미리보기 → 실제 적용 → 재생목록 생성`.
- 분류·수동 수정 결과는 DB에 저장한다. 음악 파일 이름·위치·태그 변경은 파일 정리 미리보기에서 변경 내용을 확인한 뒤 별도로 적용한다.
- 분류 상태와 파일 적용 상태를 구분해 표시한다. DB의 분류 결과 저장을 실제 파일 변경 완료로 표시하지 않는다.
- 분류 검토 화면에서 미확정 항목·이유와 보관 이동 대기/보관됨/복귀 대기 상태를 구분해 보여준다. 보관·복귀는 §3.8의 적용 절차를 따른다.
- 작업 이력에서 적용 작업의 전·후 상태와 오류를 확인하고 되돌리기를 요청한다. 복구 기본 원칙은 §8.2를 따른다.
- 중복 검토는 원래 위치에서 청취·선택할 수 있고 `_중복검토` 보관 적용도 제공한다. 파일 위치 변경과 검토 선택은 별개이며 자세한 흐름은 §11.1을 따른다.

### 15.7 화면 배치와 스타일 명세

텍스트 배치 시안이며 이미지·GUI 구현 결과가 아니다.

```
music-sorter                         음악 루트 / 전체·미분류·검토 수      ⚙ 설정
──────────────────────────────────────────────────────────────────────────────
음악 라이브러리 │ 검색 / 장르·분위기·컨셉·상태 필터        │ 곡 상세
분류 검토      │ 작업 목적 / 대상 범위 / 대상 수 / 실행    │ 원문 메타데이터
중복 검토      │──────────────────────────────────────────│ 분류·근거·수동 보호
재생목록       │ 선택  제목  아티스트  대분류  검토 상태   │ 기존 값 / 변경 제안
작업 이력      │            곡 목록·정렬·추가 로딩         │ 재생 / DB에 저장
               │──────────────────────────────────────────│
               │ 단계·완료·대기·실패 / 비용 / 정지·재개·취소│
──────────────────────────────────────────────────────────────────────────────
```

- 시작 크기 1440×900, 최소 목표 1100×720의 논리 픽셀로 설계한다. 왼쪽 탐색은 약 180, 오른쪽 상세는 약 340으로 시작하며 경계 드래그·상세 접기를 제공한다. 작은 창에서는 상세를 접어 목록 공간을 확보한다. 실제 허용 크기는 DPI 검증 후 조정한다.
- 글꼴은 Windows 한글 시스템 글꼴을 우선하고 본문 11pt로 시작한다. 설정에서 글자 크기를 바꿀 수 있게 한다. 바깥 여백 16, 위젯 간 여백 8, 기본 버튼 높이 32의 논리 픽셀을 기준으로 한다. 긴 곡명은 툴팁·상세에서 원문을 확인한다.
- 2026-10-08 전체 마무리·UI 개선 지시에 따라 고정 탐색 패널, 페이지 제목·보조 설명, 실제 DB 통계 카드, 검색/필터 도구 모음, 행 상태 배지, 선택 곡 상세 카드와 하단 재생 바를 사용한다. 밝게/어둡게·청록 강조색·여백·라운드·선형 벡터 아이콘을 통일한다. 기존 로컬 ID3 앨범 이미지가 있으면 표시하며 없으면 자체 음악 모티프를 사용한다. 이미지 외부 전송은 하지 않는다.
- 작은 창에서는 상세 패널을 접고 다시 열 수 있게 한다. 키보드 포커스·상태 텍스트·실제 기능의 검증을 디자인과 함께 수행한다. 통계·확인 상태는 실제 DB/실행 결과를 표시하며 예시 수치를 제품에 넣지 않는다.
- 밝은 테마: 배경 `#F5F7FA`, 패널 `#FFFFFF`, 본문 `#17212B`, 경계 `#D8DEE6`, 강조 `#0F766E`. 어두운 테마: 배경 `#111827`, 패널 `#1F2937`, 본문 `#F3F4F6`, 경계 `#374151`, 강조 `#2DD4BF`.
- 앱 아이콘은 2026-10-09 사용자가 선택한 4번 `레코드 아카이브`다. 황금색 둥근 사각형·검은 레코드·겹친 보관 폴더의 원본 디자인을 유지한다. 16·24·32·48·64·128·256px ICO를 실행파일 리소스와 Qt 공통 창 아이콘에 사용하고 Windows 작업 표시줄에는 고정 앱 ID를 제공한다. 루트 바로가기는 새 실행파일의 내장 아이콘을 사용한다. 원본 PNG·ICO·생성 출처는 패키지 리소스에 보관한다.
- 상태는 `완료 / 미확정 / 실패 / 처리 확인 필요 / 수동 보호 / 적용 대기`의 텍스트·아이콘으로 구분한다. 색만으로 의미를 전달하지 않는다. 알림·비용 표시를 과도하게 움직이지 않고 화면 판독·키보드 포커스를 제공한다.
- 설정의 폼 입력칸은 가용 너비를 사용하고 긴 모델 ID·경로를 표시한다. 작은 창에서는 긴 행을 줄바꿈하며 숫자 입력의 증가/감소·콤보 펼침 화살표를 밝게/어둡게 모두 명시적으로 표시한다. 공통 팝업의 확정 동작은 강조색, 적용은 보조 강조, 취소/닫기는 중립 버튼으로 구분한다. 설정은 `확인`(저장 후 닫기) / `취소`(미적용 변경 취소) / `적용`(저장 후 유지)의 Windows 순서를 유지하며 적용은 변경이 있을 때만 활성화한다. 키 즉시 저장·별도 데이터 작업은 기존 안내와 확인 절차를 유지한다.
- 음악 라이브러리의 실제 DB 위치와 데이터·복구의 사용자 데이터 위치는 이름이 있는 경로 영역으로 표시한다. 경로 입력칸은 비활성화 대신 읽기 전용으로 두어 선택·복사와 키보드 접근을 지원하고 `폴더 열기` / `경로 복사`를 제공한다. 기본 LocalAppData 위치가 업데이트와 음악 파일에서 데이터를 분리하기 위한 위치임을 안내한다. 여기에서 DB를 직접 수정하는 뷰어를 연결하지 않으며 위치 변경은 검증된 이관 절차를 따른다.
- 빈 라이브러리는 폴더 등록 안내, 키 없음은 연결 설정 안내, 검색 결과 없음은 필터 초기화를 보여준다. 실패·미확정은 대상과 이유를 바로 열 수 있게 한다. 최초 실행에서 파일 변경·유료 작업을 자동 시작하지 않는다.
- 단축 조작은 검색 이동·선택 곡 재생·상세 열기·DB 저장을 제공한다. 파일 실제 적용·복구·키 삭제는 실수로 실행되는 단일 키 단축 동작을 두지 않는다. 정확한 키 조합은 Windows 실행 화면에서 충돌을 확인해 결정한다.

### 15.8 분류 검토와 일괄 수정

- 일반 사용자의 조작 문구는 결과가 드러나는 한국어 동사로 쓴다. `동기/Batch`는 `바로 처리/나중에 결과 받기`, `DB 저장`은 `분류 저장`, `비용 예약`은 `처리 중인 요청의 예상 비용`으로 설명하고 필요한 API 모델 ID·응답 제한 등의 기술 항목에는 뜻과 단위를 붙인다. 기술 원본 JSON·식별자는 별도 상세 탭에서 확인한다. 내부 저장 값·스키마·분류/과금/확인 절차는 바꾸지 않는다.
- 분류 창은 `곡·예산 선택 → 보낼 정보와 예상 비용 확인 → 분류 시작 (유료)`으로 구성하고 처음에는 준비 안내를 보여준다. 메인 작업 순서와 혼동되는 내부 번호를 쓰지 않는다. 준비는 생성 요청을 보내지 않으며 실제 실행은 비용 확인창 뒤에만 시작한다. 결과 확인·서버 처리 취소·재시도·처리 여부 확인은 작업 상태에 따라 표시한다. 처리 결과를 알 수 없는 요청은 제공자의 미처리·미과금 확인 전 비용을 해제하거나 재전송하지 않는다.
- 닫힌 콤보박스와 편집 가능한 콤보박스 입력칸 위의 마우스 휠은 선택값을 바꾸지 않으며 바깥 스크롤 영역을 정상 이동한다. 클릭으로 목록을 열면 목록 스크롤·클릭 선택을 유지하고 키보드 선택도 유지한다. 음악 목록 맨 앞의 `No.`는 현재 검색/정렬 순서 기준의 화면 순번이며 페이지를 넘겨도 이어진다. 내부 곡 ID와 구분하고 번호 열 자체는 정렬 키로 쓰지 않는다.

- 분류 검토는 `미확정 / 낮은 신뢰도 / 외부 식별 충돌 / 수동 보호 충돌 / 제안 태그 / 파일 외부 변경` 대상을 필터로 구분한다. 파일 상태가 검토를 막으면 이유를 표시하고 먼저 해결하도록 한다.
- 상세의 각 항목에 현재 값·출처·근거·판정 상태·수동 보호·자동 변경 제안을 표시한다. `분류 저장`으로 확정한 항목만 수정하고 다른 항목을 빈 값으로 초기화하지 않는다.
- 대분류를 수동 변경하면 허용되지 않는 세부 장르를 보여주고 새 값 또는 미확정으로 함께 지정하게 한다. 잘못된 조합을 저장하지 않으며 이전 값은 이력으로 남긴다. 자동 변경과 보호 충돌은 §3.9를 따른다.
- 일괄 수정은 대상 범위·실제 건수와 수정할 항목을 먼저 선택한다. 한 값 항목은 지정·미확정, 목록 항목은 목록 교체·태그 추가·태그 제거·컨셉 해당 없음으로 제공한다. 결과 목록은 선택 개수·허용 범위를 검증하고 수정한 항목 전체를 수동 보호한다.
- 일괄 수정의 범위는 현재 페이지에서 명시적으로 선택한 곡·검색/필터 결과 전체·라이브러리 전체다. 검색에는 분위기·컨셉 포함 조건을 지원한다. 미리보기에서 실제 대상 ID·분류 버전·내용 해시·경로·변경 전후 값을 DB에 고정하고 적용 가능·충돌·변경 없음 건수를 표시한다. 필터 결과는 표시된 한 페이지로 축소하지 않는다. 미확정 목록에는 추가/제거를 실행하지 않고 목록 교체 또는 미확정 선택을 요구한다.
- 저장할 때 미리보기 뒤 DB의 판정·경로·파일 상태가 달라진 항목은 건너뛰고 이유를 남긴다. DB 수동 저장은 음악 파일 전체를 다시 읽는 작업이 아니며 외부 변경은 재스캔으로 확인한다. 실제 파일 적용 전의 전체 해시 검증은 별도 적용 절차다. 작업은 백그라운드에서 제한된 묶음으로 처리하며 취소 시 완료된 DB 판정을 유지한다. 수정 항목 전체를 수동 보호하고 곡별 이력·작업 결과를 보존한다. DB 스키마 업그레이드는 이전 DB의 검증된 백업을 만든 뒤 수행한다.
- 서로 다른 대분류의 곡에 특정 대분류 세부 장르를 일괄 적용하면 허용되는 곡·충돌 곡을 나눠 미리 보여준다. 충돌 곡은 보류하고 묵시적으로 대분류·수동 보호를 바꾸지 않는다. 저장 전 변경 요약을 확인한다.
- 음악 파일 미리보기는 곡별 원래/예정 경로·이름·ID3 장르 차이·복구 자료 필요량·충돌을 표시한다. 적용할 항목과 실제 파일 수를 명시하고 조건이 달라졌으면 새 미리보기를 요구한다. DB 저장 버튼과 실제 파일 적용 버튼의 명칭·위치를 분리한다.
- 작업 이력은 분류·파일 적용·목록 생성·복구를 구분하고 부분 실패를 파일별로 연다. DB 백업 복원과 음악 파일 되돌리기를 같은 버튼으로 합치지 않는다.

### 15.9 핵심 작업 순서와 상황별 조작 (D79)

- 메인 화면에는 `1. 음악 불러오기 → 2. 곡 정보 찾기 (선택) → 3. AI 분류 (유료) → 4. 분류 검토 → 5. 파일 정리 (선택) → 6. 재생목록 만들기`를 두 줄의 작업 영역으로 표시한다. 번호는 권장 사용 순서이며 완료율이나 강제 마법사가 아니다. 수동 분류와 기존 분류의 재사용도 가능하고 2·5는 건너뛸 수 있다.
- 각 버튼에 결과를 설명하는 짧은 보조 문구를 붙인다. 음악 불러오기는 기존 폴더의 재조회도 포함한다. 분류 검토 버튼은 이전 검색/필터를 초기화해 확인 대상 전체를 열고 곡 상세를 표시한다. 현재 선택 건수와 Ctrl/Shift 복수 선택 안내를 목록에 붙인다.
- 정보 조회·AI 분류·파일 정리 창에서 돌아와도 같은 페이지에 남은 선택 곡은 유지한다. 다음 단계가 임의의 한 곡으로 축소되지 않도록 내부 ID로 선택을 복원한다. 빈 분류 계획이나 끝난 작업에서는 `다른 곡·조건 선택`으로 새 계획을 준비할 수 있고 이전 작업 기록은 보존한다.
- 일괄 수동 수정·상세 표시 같은 보조 동작은 `선택 곡 메뉴`로 옮긴다. 복구·재시도·중단·페이지 이동 버튼은 실행 상태나 데이터가 필요할 때만 표시한다. 사이드바는 보조 화면 탐색을 유지하며 번호를 반복하지 않는다.
- 표시할 곡이 없으면 곡 상세 영역과 저장·보호 해제 조작을 노출하지 않는다. 곡을 불러오거나 검색 결과가 돌아오면 창 크기·상세 표시 선호에 따라 상세를 다시 표시한다.
- 재생목록은 메인 6번과 왼쪽 메뉴 모두 작업창을 바로 연다. 빈 안내 페이지에서 같은 기능을 다시 여는 중간 버튼을 두지 않는다. 라이브러리가 비어 있으면 선택 곡 메뉴도 숨긴다.
- 창 제목은 작업을, 창 안의 주요 버튼은 행동을 나타낸다. 정보 창은 `조회 시작`, 분류 창은 `예상 비용 확인 → 분류 시작 (유료)`, 파일 정리는 `미리보기 만들기 → 파일 변경 적용`, 재생목록은 `생성 시작`으로 쓴다. 분류 창 내부 단계에는 메인 번호를 중복 사용하지 않는다. 비용 확인·파일 적용 확인 절차는 유지한다.
- 작업창의 짧은 순서 설명과 다음 행동 안내를 유지한다. 닫기·중단 버튼이 아무 반응 없이 동작을 무시하지 않도록 실행 중 상태를 드러낸다. 유료 실행·파일 적용은 Enter의 암묵적 기본 버튼으로 실행하지 않는다.
- 재생목록의 이름·조건 선택은 `조건을 조합한 목록 추가`를 켰을 때만 표시한다. 기본 생성은 전체 라이브러리의 분류별/검토 목록과 기존 조합을 갱신한다. 추가 모드에서 이름이나 조건이 빠지면 인라인 안내하고 생성하지 않으며 선택 조건을 조용히 무시하지 않는다. 생성 중에는 입력을 잠근다.
- Microsoft [Fluent 버튼 사용 원칙](https://fluent2.microsoft.design/components/web/react/core/button/usage)과 [Windows 대화상자 조작](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/dialogs)의 작업에 맞는 동사·주요/보조 행동 구분을 참고한다. 실제 화면 검증은 §17.18에 기록한다.

## 16. 첫 버전 범위와 개발 순서

### 16.1 첫 버전 범위

- Windows 11 x64 GUI에서 한 음악 루트의 MP3를 관리한다. API 없이 스캔·검색·수동 분류·중복 비교 청취·기존 결과 내보내기를 사용할 수 있다.
- MusicBrainz·Last.fm 정보를 보완하고 OpenAI·Claude의 1차/재판정과 지원 모델의 동기/Batch 방식을 제공한다. 요청·비용·부분 실패·중단·재개를 추적한다.

- 여러 음악 루트·여러 사용자·클라우드 동기화·다른 오디오 형식·볼륨 간 음악 이관·자동 업데이트는 첫 버전에서 다루지 않는다. 오디오 분석·음악 자동 삭제·가사 스크래핑은 기존 제외 원칙을 유지한다.

### 16.3 완료 기준

다음은 출시 전 확인할 목표다. 아직 충족한 것으로 표시하지 않는다.

- **분류:** §7.3의 조정/최종 검증 집합을 구분하고 항목별 품질·자동 확정 비율·미확정 비율·재판정 효과를 보고한다. 자동 확정 대분류 정답률 초기 목표 95% 이상을 검토하되 샘플에 없는 범주는 미검증으로 표시한다. 낮은 품질을 임의 신뢰도 숫자로 숨기지 않는다.
- **파일 안전:** 이동·이름·ID3 작업과 역순 복구를 복사본에서 검증한다. 지원하는 구조는 복구 후 원본 전체 해시가 일치해야 한다. PRIV·가사·커버 등 기존 정보와 비ID3 바이트 보존을 확인한다. 지원하지 않는 구조는 이유를 표시하고 태그 적용을 막는다.
- **중단·오류:** 단계별 강제 종료, 목적지 충돌, 외부 수정, 접근 오류·디스크 공간 부족, 백업 누락·손상, API 부분 실패·응답 불확실을 검증한다. 이미 완료한 결과를 재실행하지 않고 모호한 상태를 보류하며 실제 확인 전 완료로 표시하지 않는다.
- **규모:** 30만 행의 검증용 DB로 필터·검색·정렬·집계와 목록 메모리를 측정한다. 화면은 페이지/지연 로딩하며 한 번의 조회는 최대 500행을 기준으로 한다. 일반 목록 조회·인덱스 기반 검색의 1초 이내 응답을 목표로 하되 장치·데이터·조회 조건·p95를 보고한다. 전체 해시 스캔 시간은 읽기량·저장 장치와 함께 따로 측정하고 API 1건/초 제한을 로컬 성능과 섞지 않는다.
- **화면:** 밝게/어둡게·한글 긴 곡명·작은 창·100/125/150/200% DPI·키보드 이동·상태 텍스트·오류 안내를 실제 Windows 렌더에서 확인하고 필요하면 스타일을 수정한다. 내장 MP3 청취·A↔B 전환·파일 적용 전 핸들 해제를 검증한다.
- **출력:** 곰오디오·삼성 뮤직에서 장르 표시, 한글 파일명, 폴더째 복사한 m3u 상대 경로·`/` 구분자·인코딩을 확인한다. 차이가 있으면 검증한 출력 프로필을 제공한다. 문서의 기대 동작만으로 호환 확인을 대신하지 않는다.
- **설정·배포:** Windows 자격 증명 저장·교체·삭제·오류 시 보류, 키 없는 로컬 기능, 비밀값 없는 로그·내보내기를 확인한다. Python을 별도 설치하지 않은 Windows에서 ZIP 실행·MP3 재생·데이터 보존·스키마 업그레이드를 검증하고 의존성·라이선스 고지를 포함한다.

## 17. 구현·검증 현황

### 17.3 남은 구현·검증

- 외부 음악 조회·구조화 출력·Batch·비용·자동 제안 충돌 처리의 첫 구현은 §17.7에 기록한다. OpenAI의 실제 계정 연결·두 서비스 생성 권한·실제 사용량·모델별 기능·분류 품질은 남은 검증이다. API 키·작업 예산 없이 실제 유료 검증을 시작하지 않는다.
