## 2026-09-30 ~ 10-01: 설계 논의 1차

### 1. 출발점

- 사용자가 임시 샘플 폴더(mp3 454곡)를 보여줌. 모두 `아티스트 - 제목.mp3` 형식, 하위 폴더 없음.
- 문제의식: 지금은 수백 곡이지만, **수십만 곡**이 되면 분류가 필요하다.
- 진행 방식: **사용자가 "개발 시작"이라고 하기 전까지는 의논만 한다.**
- 이후 샘플 폴더는 임시용이라 설계 기준으로 삼지 않기로 함.

### 2. 분류 기준과 결과 형태

- 처음 제시한 선택지: 아티스트·앨범 / 장르 / 분위기·템포 / 중복 정리.
  결과 형태로는 (A) 폴더 이동, (B) DB·태그만, (C) 둘 다를 제시했고 C를 추천.
- 사용자 요구:
  - **장르별 분류**가 목적. 외부 음원 DB나 검색, LLM API 활용 예상.
  - 기본은 가요 / 팝 / 재즈 음악 / 재즈 보컬 / 뉴에이지 / 클래식 정도.
  - 나중에는 느낌별(신나는, 조용한, 캐롤 등), 재즈 세부 장르(보사노바, 라틴 등)까지.
  - 세부 분류는 폴더보다 **태그**로. 폴더째 재생과 태그별 재생을 골라 쓰고 싶음.
  - 전체 목록과 메타데이터를 관리하는 **로컬 DB(SQLite)**.
- 규모 이슈 정리: 30만 곡 ≈ 2.4TB, MusicBrainz 초당 1건 제한(약 3.5일), 중단 후 재개 필요, 동기화 폴더 부하.

### 3. 샘플 메타데이터 비교

두 파일을 비교한 결과 출처에 따라 메타데이터가 크게 다름을 확인 (SPEC §4).

| 항목 | 잔나비-08-주저하는 연인들을 위해 | 한형일 - 하루동안 |
|---|---|---|
| 추정 출처 | 멜론 정식 다운로드 | 변환 파일로 추정 |
| 태그 | 제목, 아티스트, 앨범, 트랙, 발매일, 장르(Rock), 가사, 저작권, 멜론 ID | 제목, 아티스트, 커버만 |
| 음질 | 320kbps, 44.1kHz | 320kbps, 48kHz, LAME 3.100 |

- 전체 454곡 중 멜론 파일 1곡, 장르 태그 1곡.
- 같은 곡(잔나비)이 두 벌 있으며 길이가 다름 → 해시·길이로는 중복을 못 잡음.
- 결론: 파일 내 장르 태그는 믿을 수 없고, 메타데이터 등급 개념과 중복 검토가 필요.

### 4. 분류 체계 확정 과정

- 오디오 분석(Essentia 등)을 선택지로 제시했으나 사용자가 **불필요**로 결정. 외부 정보 + LLM만 사용.
- 사용자가 장르 / 분위기 / 컨셉 3종 기준을 원함. 예: "가요/인디/조용한".
- OST는 너무 세부적이라 장르에서 제외 → 컨셉 태그로.
- 재즈 음악 / 재즈 보컬 → 대분류 `재즈` + 속성(보컬/연주) + 세부 장르 `보컬재즈`로 정리.
- **CCM 추가** 요청. CCM 안에서도 노래와 연주곡 구분 필요 → 보컬/연주를 모든 장르 공통 속성으로 승격.
- **싸이 곡 예시** 검토에서 발견한 점:
  - `파티/응원` 컨셉이 없음 → 추가, 그리고 "목록 외 제안 태그" 방식 도입.
  - 같은 아티스트도 곡마다 장르가 다름("기댈 곳"은 발라드 성향) → 곡 단위 판정.
  - `댄스/아이돌` 명칭이 싸이에 어색함 → `댄스`로 변경.
  - 세부 장르 경계가 모호함("예술이야") → 세부 장르 최대 2개 허용.
- **트로트를 대분류로 분리**. 임영웅처럼 트로트와 발라드를 오가는 가수가 있어 대분류조차 곡 단위로 판정해야 함을 재확인.

### 5. 재생 환경과 출력 방식

- 사용 환경: PC는 **곰오디오**, 폰은 **삼성 뮤직**. 폰에는 폴더를 **통째로 복사**.
- 두 앱 모두 태그 필터 재생이 약함 → ID3 장르 필드에는 대분류만, 나머지는 **m3u 재생목록**으로.
- m3u 개념 설명: 음악 데이터 없이 곡 경로 목록만 담은 텍스트 파일. 곡 복사 없이 여러 재생목록에 같은 곡을 넣을 수 있음.
- 상대 경로 m3u를 음악 폴더 최상위에 두면 폴더째 복사해도 동작.
- 태그를 파일에 자주 쓰면 폰 재복사가 반복되므로 파일 기록은 안정된 뒤 한 번에.

### 6. 파일 관리

- 파일 이름 정리는 지금 수작업으로 하지 않고 **프로그램 기능**으로. 형식은 `아티스트 - 제목.mp3`.
- 중복 곡은 **사용자가 직접 듣고 판단**. 검토 폴더로 모으고, 같으면 음질 좋은 쪽 선택.
  - 비트레이트 숫자만으로는 판단 불가(저음질 재변환 파일 가능) → 출처 신뢰도 > 비트레이트 > 메타데이터 완성도 순으로 추천.
- 폴더 구조: **대분류 폴더**로 나누기로 결정.
- Windows 고려 사항: 맥에서 온 파일의 한글 자모 분리(NFD) 정규화, 금지 문자 처리, 긴 경로.

### 7. 프로젝트 설정

- 이름 후보 1차: melodex(추천), cratedigger, tunetag, musicshelf, gyeol.
- 사용자가 "한국인도 알아보기 쉬운 단어"를 원함 → 2차: music-sorter(추천), music-tagger, songbox, playlist-maker, my-music-library, norae-box.
- **music-sorter**로 확정, GitHub 공개 저장소 생성. 민감 정보는 `.env`로 분리.
- 문서 체계: SPEC(설계 정본), DECISIONS(결정 이유), HISTORY(논의 흐름), CLAUDE.md(작업 규칙). SSOT 원칙 적용.
- 커밋은 작업 단위마다 자동으로, AI 공동 기여자 표기 없이.

### 8. LLM과 개발 언어

- LLM 수준 검토: 분류 자체는 쉽지만 덜 알려진 한국 곡에 대한 지식이 관건.
  최저가 등급은 모르는 곡을 지어낼 위험 → "저가형 중 상위" 등급 권장.
- 30만 곡 비용 추정 비교 (SPEC §7.4): Haiku 4.5 약 $105, GPT-5.4 mini 약 $90, GPT-5.4 nano 약 $25, Gemini 3.1 Flash-Lite 약 $30, Sonnet 5.5 약 $210.
- 2단계 방식(저가 모델로 전체 → 신뢰도 낮은 곡만 상위 모델) 제안.
- 사용자 결정: **Claude Haiku 4.5** + 재판정은 Sonnet 5.5.
- 개발 언어: Python / C# / Node.js 비교 → **Python** (mutagen, sqlite3 내장, LLM SDK, 개발 PC에 3.13 설치됨). CLI로 시작.

## 2026-10-06: 파일 식별 합의와 Windows GUI·설정 기획

- 앞선 논의에서 전체 파일 해시는 ID3 수정으로 달라지므로 영구 식별자로 부적합하다는 점을 설명하고, 내부 파일 ID와 현재 경로·해시를 구분하는 방식을 제안했다.
- 사용자가 "좋은 것 같다"고 동의하여 파일 식별 원칙에 반영했다. 외부 이동·수정 후 재스캔 연결 규칙과 복구 정책은 다음 논의 대상으로 남겼다.
- 사용자가 Windows GUI로 개발하도록 방향을 바꾸고, 톱니바퀴 설정 메뉴와 LLM API 입력, OpenAI·Claude 선택 지원을 요청했다. 기존 CLI 우선 계획은 대체되었다.
- 개발 플랫폼은 PySide6·WPF·WinUI 3·Avalonia·Tauri·Wails·Electron을 비교하고 Python + PySide6(Qt Widgets)를 추천했다. **추천 단계이며 사용자 확정 전**이다.
- API 연결 등록과 1차·재판정 모델 선택을 분리하고, 라이브러리·분류/비용·외부 정보·파일 출력·데이터 복구를 포함한 설정 기획을 SPEC §15에 검토안으로 정리했다.
- GUI API 키는 Windows 자격 증명 저장소에 보관하는 방식을 제안했다. 기존 `.env` 전용 규칙과의 조정은 미결정으로 남겼다.
- 이번 작업은 설계 문서와 설정 예시만 갱신했다. 구현 코드 작성·패키지 설치·음악 파일 변경·API 호출은 하지 않았다.

### GUI 플랫폼·디자인 확정과 다음 논의

- "스타일을 직접 다듬어야 한다"는 설명이 사용자에게 디자인 작업을 맡긴다는 뜻인지 질문이 나왔다. 화면 설계부터 색상·위젯 스타일 구현·실행 화면 검증까지 개발 범위에 포함할 수 있음을 설명했다.
- 사용자가 "그렇게 가자"고 동의하여 PySide6(Qt Widgets)와 디자인 제작 범위를 확정했다. 설정 메뉴의 세부 동작·키 저장 방식·배포 도구는 계속 검토안이다.
- 남은 항목은 개발 전 합의할 동작·화면·복구 정책과, 개발 초기 샘플로 검증할 정확도·앱 호환성·성능 항목으로 나눠 SPEC §14를 정리했다. 미결정 사항을 임의로 채택하지 않았다.
- 다음 논의는 변경 전 상태 보존·되돌리기 정책부터 제안한다. 메인 화면 시안과 검토 흐름을 구체화할 때 복구 범위를 반영하기 위해서다.

### 복구 기본 원칙 확정과 메인 화면 제안

- 경로 충돌 시 덮어쓰기 금지, ID3 원본 보관, 파일별 상태 확인 후 재개, 외부 수정 시 자동 복원 중단의 네 가지 원칙을 제안했고 사용자가 "좋아"라고 동의했다. SPEC §8.2에 반영했다.
- DB 백업만으로 음악 파일 복구를 대체하지 않는다는 점을 명시했다. 원본 저장·보관과 실패 복구·다중 작업 되돌리기의 구체적 절차는 아직 미결정이다.
- 다음 논의로 메인 화면의 탐색 메뉴·곡 목록·상세·작업 상태와 `스캔 → 분류 → 검토 → 미리보기 → 적용 → 재생목록` 흐름을 제안했다. SPEC §15.6에 검토안으로 남겼다.

### 메인 화면·작업 흐름 확정과 재스캔 제안

- 사용자가 "오케이"라고 동의하여 메인 화면의 기본 구성, 작업 대상 범위 선택, 분류 결과 저장과 파일 적용의 분리 흐름을 확정했다. 시각 시안과 세부 조작은 후속 검토 대상으로 남겼다.
- 다음 논의는 외부 이동·수정 후 재스캔이다. 정상적으로 확인한 범위와 확인 불가 범위를 구분하고, 동일 해시의 1:1 연결·복사본·외부 변경·모호한 연결·누락을 각각 처리하는 검토안을 SPEC §8.3에 정리했다.
- 경로·해시만으로 외부 이동과 복사 후 원본 제거를 구별하지는 못하므로, 1:1 연결은 동일 내용에 기존 관리 기록을 이어가는 운영 규칙으로 제안했다. 재스캔만으로 유료 재분류를 실행하지 않는 방향도 함께 제안했다.

### 재스캔 규칙 확정과 미확정 분류 제안

- 사용자가 "기존 분류를 이어간다"는 의미를 질문했다. 이동한 파일의 내부 ID와 DB에 저장한 장르·분위기·컨셉·수동 수정은 유지하고 경로만 갱신한다는 뜻으로 설명했다.
- 사용자가 "그래 이 규칙으로 확정"이라고 동의하여 재스캔 기본 규칙을 확정했다. 해시 계산 최적화·스캔 도중 변경 감지는 상세 설계 대상으로 남겼다.
- 다음 논의는 분류 기준이다. 항목별 미확정 상태를 허용하고 알고 있는 항목의 결과는 보존하는 방식을 SPEC §3.8에 검토안으로 정리했다. 대분류 경계·우선순위는 별도 논의하기로 제안한다.

## 2026-10-07: 미확정 곡의 별도 보관

- 사용자가 미확정이 LLM 검수 이후에도 분류되지 않은 경우인지 질문했다. 1차 분류·상위 모델 재판정 이후에도 항목별로 미확정이 남을 수 있으며, 재판정 대기와 사람 검토 필요 상태를 구분한다고 설명했다.
- 사용자가 "미확정은 따로 폴더링 해서 보관하는 방식으로 가자"고 요청했다. LLM 처리 이후 미확정 항목이 남은 곡은 `_미확정`에 모으고 기존 확정 정보는 DB에 보존하는 것으로 반영했다.
- 대분류가 알려져도 미확정 항목이 있으면 별도 보관한다. 앞선 대분류 폴더 유지 검토안은 대체되었다. 검토 후 해결되면 대분류 폴더로 복귀하는 흐름이며, 두 이동 모두 기존 미리보기·실제 적용·이력 기록 원칙을 따른다.
- `_미분류`는 분류 전, `_미확정`은 LLM 처리 이후 검토 대상으로 역할을 나눴다. API 오류·중단은 미확정 판정과 구분한다.
